One shared JSON-file loader for the 13 node stores that hand-rolled it independently (issue #922).

`account-pin-store.ts`, `agent-profile-store.ts`, `ci-watch-store.ts`, `mcp-config-store.ts`, `native-tracker-store.ts`, `permission-policy-store.ts`, `session-store.ts`, `session-template-store.ts`, `snippet-store.ts`, `spend-cap-store.ts`, `spend-ledger-store.ts`, `test-runner-config-store.ts`, and `tracker-mode-store.ts` each independently implemented "read this JSON file off disk, treat a missing file as empty, wrap a parse failure in my own typed error" (#652's own duplicate sweep flagged it, filed separately as #922 for per-store review). The wording had already drifted: 8 said "config file ... is not valid JSON", 5 said plain "file ... is not valid JSON" for the identical condition.

All 13 now go through a new `loadJsonFile<T>(filePath, defaultValue, parse, makeError)` in `packages/node/src/json-store.ts`. Each store keeps its own on-disk default, its own `validateFile` schema, and its own `Error` subclass; the loader only owns the three steps that were byte-for-byte identical: no file -> the caller's default, a syntactically corrupt file -> the caller's error with one wording ("file ... is not valid JSON"), everything else -> the caller's own schema validation. I settled the wording on "file" rather than "config file": several adopters persist state that was never really configuration (a spend ledger, an in-flight CI-watch set, session records), so "file" is the word that fits all 13 without stretching "config" over the ones that aren't.

Four other JSON-file readers in `packages/node` were checked and deliberately left out, because they don't share this loader's "throw a typed error on a corrupt file" contract: `SessionTitleStore` and `FileKeyringBackend`/`SshTargetStore` all silently degrade to an empty/default value on a corrupt file by design, and `DeviceTokenFileStore` (already checked and excluded by issue #922 itself) returns `undefined` on a parse failure rather than throwing. Bending the loader to also cover "sometimes throw, sometimes swallow" would blur the one guarantee it exists to make, so none of the four were touched.

No store's observable behaviour changed: every store still throws its own `Error` subclass for a corrupt file and its own default for a missing one; only the shared parse-failure wording changed, and no existing test asserted that literal wording (only the error class via `toThrow(XError)`), so all 13 stores' existing test suites pass unchanged. `json-store.test.ts` is new and covers the loader directly: missing file returns the default without calling `parse`, a well-formed file is handed to `parse` with its own `filePath`, a corrupt file throws the caller's error with the shared wording, and an error thrown by `parse` itself (schema validation) propagates unwrapped rather than being re-wrapped by `makeError`.

Verified: `pnpm --filter @loombox/node exec vitest run` (175 files, 1908 tests passed, 1 pre-existing skip), `pnpm --filter @loombox/node typecheck` (0 errors), `pnpm exec eslint` on all 15 changed/added files (clean), full `pnpm format:check` (clean).
