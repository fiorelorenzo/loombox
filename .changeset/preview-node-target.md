A local resident node can now target preview without colliding with a production node on the same machine (issue #867, epic #863)

`packages/node/src/node-environment.ts` is new: `NodeEnvironment` (`'production' | 'preview'`) and four pure functions — `defaultUnitName`, `defaultLaunchdLabel`, `defaultBaseDirName`, `collisionFreeNodeId` — that turn "which environment is this node for" into collision-free defaults for the four things #867 named as colliding today:

- **The unit name / launchd label.** `createSystemdLocalSupervisorBackend`/`createLaunchdSupervisorBackend` (`packages/node/src/local/systemd-local-supervisor-backend.ts`, `packages/node/src/launchd/launchd-supervisor-backend.ts`) take a new optional `environment` field. Left unset, both resolve to exactly the pre-existing names (`loombox-node.service`, `dev.loombox.node`) — no behavior change for an existing devbox. Set to `'preview'`, they resolve to `loombox-node-preview.service` / `dev.loombox.node-preview` instead, so `systemctl --user restart loombox-node` can never hit the wrong one.
- **The install root and state dir.** Both backends now default `baseDir` to `~/.loombox` (production) or `~/.loombox-<environment>` (otherwise) and `stateDir` to `<baseDir>/node` — a whole separate `versions/`/`current`/`node` tree per environment, so `uninstall()`'s `rm -rf` of one environment's bundle/state can never reach the other's. `packages/node/src/ssh/verify-and-persist.ts`'s `defaultNodeStateDir()` takes the same optional `environment` parameter (default `'production'`, so every existing caller is unaffected) and resolves the same way, both under `XDG_STATE_HOME` and the plain home-dir fallback.
- **The keyring entry.** Already keyed by state dir (`identity.ts`), so a distinct state dir per environment already gives a distinct entry — now exercised end to end by the two-environment scratch-unit test below rather than assumed.
- **The node id.** `provisionLocalNode` (`packages/node/src/local/provision-local-node.ts`) takes the same `environment` field and runs the caller-supplied `nodeId` through `collisionFreeNodeId`, so an operator who reuses the same id for both environments (the natural thing to type twice) still gets two distinguishable rows in the account's node list.

Every one of these is a default only — a caller that already sets `unitName`/`baseDir`/`stateDir`/`label` explicitly keeps full control, `environment` just narrows what happens when none of those are given.

Verified: `pnpm --filter @loombox/node exec vitest run` (167 files, 1827 passed, 1 skipped — `attachments-e2e.test.ts`'s pre-existing, unrelated flake, already being fixed on `test/attachments-flake`/#886), `pnpm --filter @loombox/node typecheck` (0 errors), `pnpm --filter @loombox/desktop typecheck` (0 errors, confirms the widened `LaunchdSupervisorBackendOptions`/`LocalProvisionOptions` signatures stay compatible with the desktop bridge), `pnpm exec eslint` on every changed file (clean), full `pnpm format:check` (clean).

The strongest proof is a new real integration test, `systemd-local-supervisor-backend.test.ts`'s `"issue #867, two environments concurrently, scratch units"` block: against the real `systemctl --user` on whatever machine runs it (skipped where unavailable), it installs two genuinely separate scratch units — one per environment, both using this module's own default derivation — confirms both are `running`, restarts the preview one and confirms production's status and on-disk identity are untouched, then uninstalls preview and confirms production is still `running` with its own bundle and identity intact. Every identifier is scratch (pid-suffixed unit names, a throwaway `os.tmpdir()` tree) — this devbox's real `loombox-node.service`/`~/.loombox` were never touched by any test in this change.
