Windows local process-tree kill for a running session (issue #940, filed out of #659; epic #653).

On POSIX, `test-runner-process.ts`'s `startLocalRun` spawns the launched command with `detached: true`, making it the leader of its own process group, and `cancel()` reaches the whole tree via the negative-pid convention (`process.kill(-pid, ...)`, issues #642/#645/#646). Windows has no process groups in that sense, so before this change a cancelled Windows session left every forked grandchild running — the same class of leak this repo has already paid for once on Linux (1917 orphaned fixture children, 17GB of RAM, before #642).

I read how the existing seam works before touching it: `test-runner-process.ts`'s own `-child.pid` group kill, `RemoteProcessRunner`'s `setsid` branch in `buildStopScript`, and `remote-sessions-test-sandbox.ts`'s own reaper. All three converge on the same shape: signal a kernel-tracked group, not a walked PID tree. The Windows equivalent is a Win32 Job Object, and this plugs into the exact same seam rather than becoming a parallel mechanism: `startLocalRun` now dispatches on `process.platform`, and `windows/windows-job-runner.ts`'s `startWindowsLocalRun` takes the identical `StartRunOptions` in, returns the identical `RunHandle` out.

How it works: `buildWindowsJobLaunchScript` renders a PowerShell script (no native addon exists in this repo, and none was added — per #940's own framing, the alternative is shelling out to a small helper process) that P/Invokes `kernel32.dll` via an inline `Add-Type` C# compile to create a Job Object with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`, assigns the PowerShell host itself to it, then runs the caller's command via `cmd.exe /d /c`. Every process that host goes on to fork — `cmd.exe` and anything _it_ forks, at any depth — automatically inherits job membership (nothing here sets `CREATE_BREAKAWAY_FROM_JOB`). `cancel()` then just terminates the wrapper's own pid (`child.kill()`, which Node maps unconditionally to `TerminateProcess` on win32); that closes the wrapper's only handle to the job, and the kernel takes every remaining process in it down as a documented side effect. No `taskkill /PID <pid> /T /F` anywhere — #940 explicitly rejects that shortcut, since its parent-PID/creation-time walk is exactly the class of bug #642 fixed on POSIX (a re-parented or PID-reused child can slip past it). Argv is passed via `-EncodedCommand` (base64 UTF-16LE), so the generated script — which itself embeds a C# heredoc and the caller's own shell command — never has to survive a second, lossy round trip through cmd.exe's or PowerShell's own command-line requoting.

What's tested, all of it without a Windows host: `escapePowerShellSingleQuoted`'s escaping (the only rule a PS single-quoted literal has); `buildWindowsJobLaunchScript`'s generated content by direct string assertion — the job-object/kill-on-close calls are present, `taskkill` and `BREAKAWAY` are both absent, the command is correctly embedded and escaped, CRLF-terminated, ends by propagating `$LASTEXITCODE`; `buildWindowsPowerShellArgs`'s `-EncodedCommand` value decoded back and compared byte-for-byte against `buildWindowsJobLaunchScript`'s own output; `classifyWindowsExitCode` against cmd.exe's real `9009` ("not recognized...") and this module's own job-setup-failure sentinel; and `startWindowsLocalRun`'s full `RunHandle` contract — spawn argv, stdout streaming, exactly-once `onExit`, cancel calling `child.kill()` with no pid argument (never a negative pid, since there is no process group to signal), and every error path — against a mocked `node:child_process.spawn`, since no Windows host exists to spawn a real one. `test-runner-process.ts`'s own dispatch (`startLocalRun` calling into `startWindowsLocalRun` on `win32` and never off it) is covered separately with that module mocked, so none of the existing real-process POSIX tests in the same file are affected.

What's genuinely unverified, stated plainly: there is no Windows machine anywhere in this environment, same constraint #659 shipped under. The `Add-Type` C# compile has never actually run, the P/Invoke struct marshaling (`JOBOBJECT_EXTENDED_LIMIT_INFORMATION`, sized via `Marshal.SizeOf` to stay correct on 32- vs 64-bit) has never been exercised against the real kernel32 ABI, and the central claim this whole approach depends on — that terminating the job-holding wrapper process actually cascades to kill every process still in the job — has never been observed happening. Nested-job support (default since Windows 8 / Server 2012) is assumed, not checked. Real-machine verification is #939 (filed for #659 under the identical constraint) rather than a new, duplicate tracking issue; I've left a note there pointing at this surface.
