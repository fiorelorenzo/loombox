Windows-local resident node: a Task Scheduler `SupervisorBackend` behind the seam #654 introduced and #658 filled in a second time (issue #659, epic #653).

I read #654 and #658 before designing this one, since the seam was explicitly written against launchd and proved a second time by systemd-user, and issue #659 exists specifically to check that seam against the one genuinely non-POSIX platform before anything Windows-specific got baked into it above the interface. It didn't need to change: `packages/node/src/windows/windows-provisioning.ts` and `windows-supervisor-backend.ts` are two new files implementing `SupervisorBackend` unchanged, exactly like the module's own doc comment promised.

What's different from the other two, and why:

- **Task Scheduler with a `LogonTrigger`, not a Windows Service.** A service needs admin and, running as `LocalSystem`, is the wrong place for this node's own DPAPI-backed Credential Manager entries (scoped to the interactive user, not a service account). A per-user scheduled task under `InteractiveToken`/`LeastPrivilege` needs no admin at all and is the direct analogue of launchd's own `LaunchAgent`.
- **No `EnvironmentVariables` field on a Task Scheduler action at all.** `windows-provisioning.ts` generates a small `.cmd` launcher (`set "NAME=VALUE"` per env var, then the real command) instead; the task's own action always invokes `cmd.exe /d /c "<launcher>"`.
- **`ExecutionTimeLimit` defaults to 72 hours** (Microsoft's own docs) — silently fatal for a process meant to run indefinitely. Always set to `PT0S`.
- **A `LogonTrigger` only fires at the next logon**, unlike `RunAtLoad`/`enable --now`. `executeWindowsTaskProvisioning` always follows a successful `/Create` with an explicit `/Run`, the only way to satisfy `install()`'s "already running" contract right now.
- **No "restart forever" primitive** — `RestartOnFailure/Count` is a schema-capped `unsignedByte` (max 255). A generously large but real, finite bound (200), stated as a real platform gap rather than implied away.
- **No POSIX shell**, so `ssh/local-process-transport.ts` isn't reusable at all. Every `WindowsTaskIo` method is argv-based (`execFile`, never a shell string) — the same convention `LaunchdIo` already uses, for a different reason (there is no shell to quote for here at all). `winQuoteArg` is this module's own `CommandLineToArgvW`-compatible quoting for the two places a single command-line string is unavoidable.
- **Atomic swap by directory junction, not a symlink.** A plain symlink needs admin or Developer Mode on Windows; `install-layout.ts` gains `createWindowsInstallLayoutDriver`, identical to the existing local driver except `activateVersion` uses `fs.symlink(..., 'junction')` with an absolute target (junctions require one, unlike the POSIX driver's deliberately relative one) and removes the old link with `rmdir`, falling back to `unlink` — verified for real on this Linux devbox that `'junction'` is silently ignored off-Windows (a genuine symlink lands instead) and that `rmdir` on it fails `ENOTDIR`, which is exactly the case the fallback exists for.

What's tested: every generator (`generateWindowsTaskXml`, `generateWindowsLauncherScript`, `winQuoteArg`) against direct string assertions; the full plan/execute decision logic (`noop`/`install`/`update`/`unsupported`) against an in-memory `WindowsTaskIo`; the full `SupervisorBackend` surface (install staging+registration, start, stop, status parsing, survivesReboot, uninstall, idempotency, environment collision-freedom) against that same fake plus an in-memory `InstallLayoutDriver`; `createWindowsInstallLayoutDriver` against real `node:fs` I/O on this POSIX host (real stage/activate/re-activate/rollback, the absolute-target assertion, and the rmdir→unlink fallback actually exercised via a real repeated activation); a new backend added to `supervisor-backend.test.ts`'s existing cross-implementation contract test (which I also filled in for #658's own systemd-user backend, missing from it since that issue landed).

What's genuinely unverified, stated plainly rather than implied away: there is no Windows machine anywhere in this environment. `schtasks.exe` has never actually run; the generated Task XML has never actually been imported by real Task Scheduler; the `.cmd` launcher has never actually executed under `cmd.exe`; the junction has never actually been created on real NTFS; DPAPI/Credential Manager separation between two nodes on one machine relies entirely on `keyring.ts`'s existing `@napi-rs/keyring` abstraction (already cross-platform, untouched by this change, itself unverified on Windows for the same reason). None of that is a soundness claim — it's a testability boundary. Filed as #939: a real Windows machine actually running this backend's tests and the real click-through, the same "verified only to the IPC boundary" honesty #654's own closing comment used for macOS.

Also filed separately as #940, and explicitly out of scope for this seam: the session-level process-tree kill for a _local_ Windows target (the `startLocalRun`/`LocalExecutionTarget` mechanism `child_process.spawn({ detached: true })` + negative-pid `process.kill` uses today, POSIX process groups only) has no Windows equivalent yet. That's a different subsystem than `SupervisorBackend` — none of the three existing backends' own `stop()`/`uninstall()` touch it either (systemd's own generated unit uses `KillMode=process`, deliberately only the main process) — and doing it properly needs Win32 Job Objects, not a best-effort `taskkill /T`, exactly as #659 itself warns.
