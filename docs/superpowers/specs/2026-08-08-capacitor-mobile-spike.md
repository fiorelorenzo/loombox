# Capacitor mobile wrap — v3 gateway spike (issue #281)

Date: 2026-08-08

Status: **spike complete.** Recommendation: **proceed, with three named changes** (see
Recommendation below) before the real v3 mobile epic (#34) builds product on top of this
scaffold.

## What this answers

AGENTS.md and SPEC §5.4/§10/§10.1 already decided the architecture: `apps/mobile` is the
same SvelteKit PWA wrapped with Capacitor, no Expo, no React Native. What was not decided,
and what issue #281 asked a spike to settle with evidence rather than opinion, is what
wrapping it actually costs — does the build work, is the WebView a secure context (the
whole E2E model depends on `crypto.subtle`), what happens to the AMK in WebView storage,
and what an app suspend does to the relay's WebSocket.

Every claim below is either something I ran, with the exact command and output it produced,
or is explicitly marked **[unverified]** with the reason and what it is grounded in instead.

## What I built

`apps/mobile` (was a placeholder package: `PACKAGE_NAME === '@loombox/mobile'` and nothing
else) is now a real Capacitor 8.5.0 project:

- `capacitor.config.ts` — `appId: 'dev.loombox.app'`, `webDir: 'www'`, explicit
  `server.androidScheme: 'https'`.
- `src/diagnostics.ts` — a small, pure, unit-tested runtime probe (`runDiagnostics`,
  `probeWebSocketRoundTrip`) answering exactly the questions below: origin/scheme,
  `isSecureContext`, `crypto.subtle` presence, `localStorage` round-trip, and a **live**
  WebSocket open/send/receive round trip (not just "the constructor exists").
- `www/index.html` + `src/www-bootstrap.ts` — the diagnostics page, bundled by
  `scripts/build-www.mjs` (esbuild) into `www/diagnostics.js`. This is deliberately **not**
  the real loombox PWA — see "Does the build work at all" below for why — it stands in as
  the `webDir` so `cap add`/`cap sync` have something real to bundle and so the WebView
  questions below have a real WebView to answer them in.
- `android/` and `ios/` — generated by `cap add android`/`cap add ios`, gitignored. Nothing
  in either tree is hand-edited (no plugin, no native code changes), so regenerating them
  loses nothing today. The tradeoff, stated plainly since whoever picks up #34 inherits it:
  the moment a plugin, an `Info.plist` entry, or an icon set gets hand-edited, that tree
  stops being derived output and has to come out of `.gitignore` and become real source, or
  a future `cap sync` silently discards the edit.

## Does the build work at all, and what does the layout look like?

**Yes, on both platforms, with one real blocker on each that I hit and resolved.**

### The webDir problem — why this isn't the real PWA yet

`apps/web` uses `@sveltejs/adapter-node` (SPEC-driven: it's deployed behind a Node process
on prodbox). I built it for real (`pnpm --filter @loombox/web build`) and inspected the
output: `build/client/` has the compiled JS/CSS/fonts/service-worker, but **no
`index.html`** — because SvelteKit's default SSR renders the HTML shell per-request from
`build/index.js`, it never writes a static one. Capacitor's `webDir` needs a directory a
WebView can load directly with no server behind it, so `cap sync`-ing `apps/web/build`
as-is doesn't produce a bootable app; there's nothing for the WebView to open.

I tested the fix, not just proposed it: `apps/web` has **zero** `+page.server.ts`,
`+layout.server.ts`, or `+server.ts` files anywhere (checked), meaning nothing in the app
actually depends on per-request SSR — the real data (sessions, transcripts) all comes
live over the relay WebSocket after hydration, same as the Electron desktop shell already
assumes. So I swapped in `@sveltejs/adapter-static` with `fallback: 'index.html'` plus
`export const ssr = false` at the root layout, in a throwaway local edit (reverted before
committing anything — this is not currently apps/web's shipped adapter, changing that is a
bigger call than spike scope), and built:

```
> Using @sveltejs/adapter-static
  Wrote site to "build-static"
```

producing a real `build-static/index.html` (2.1 MB total with fonts/icons/service worker).
**This is the "proceed with a named change" item**: give `apps/mobile` (or `apps/web`) a
maintained static-SPA build target using this exact adapter swap, rather than the
diagnostics-page stand-in this spike ships with. I did not wire it up as a permanent
pipeline in this PR — that's real per-package build-config surgery, not something a spike
should commit to silently.

## `crypto.subtle` and the AMK — is the WebView a secure context?

**iOS: yes, live-verified on a real simulator, not inferred.** Installed and launched the
built app (`xcrun simctl launch "iPhone 17" dev.loombox.app`), screenshotted the running
diagnostics page (`xcrun simctl io "iPhone 17" screenshot`) and read every line back:

```
PASS — origin: capacitor://localhost
PASS — isSecureContext: true
PASS — crypto.subtle present: present
PASS — localStorage round-trip: read back own write
PASS — WebSocket constructor present: present
PASS — WebSocket round trip: open + echoed "Request served by 4d896d95b55478"
```

That last line is a **live** WebSocket round trip against a public echo server
(`wss://echo.websocket.org` — deliberately not loombox's own relay, this diagnostics page
has no account/session context), confirming the WebView can actually open a socket and
move data over it, not just that the `WebSocket` constructor exists. `capacitor://localhost`
matches Capacitor's documented iOS default (`https:` is reserved for real remote loads in
WKWebView, so a custom scheme is the only option there) — and Chromium/WebKit's
secure-context check is scheme + host based, not "was there a real TLS handshake", which is
exactly what the live `isSecureContext: true` / `crypto.subtle present` results confirm in
practice, not just in the spec.

(First launch attempt hit a bare Capacitor-native "JS Eval error" log line with no detail
and the page stuck on "running..." — added a `try/catch` + `window.onerror` handler that
renders the failure into the DOM itself, since there's no interactive Safari Web Inspector
reachable headless over SSH. The identical diagnostics logic then passed cleanly on
rebuild, so that first error was transient/Capacitor-internal, not a bug in the probe —
noted here rather than silently dropped, since it's the kind of thing that reads like a
real finding if you only see the second, clean run.)

**Android: [unverified at runtime] — no emulator on this box, confirmed above.** Grounded
in Capacitor's own source rather than left as an assumption: `capacitor.config.ts` pins
`server.androidScheme: 'https'` (Capacitor 5+'s own default, kept explicit rather than
implied). `WebViewLocalServer.java`'s class doc comment states the mechanism directly:
"Helper class meant to be used with the `android.webkit.WebView` class to enable hosting
assets, resources and other data on 'virtual' `https://` URL. Hosting assets and resources
on `https://` URLs is desirable as it is compatible with the Same-Origin policy" — it
intercepts `https://localhost/*` in `shouldInterceptRequest` and serves the bundled
`webDir` locally, no real TLS handshake, the same "intercept and serve as if from a real
origin" trick that the iOS `capacitor://` scheme uses and that I *did* verify live. Given
both platforms rely on the identical class of mechanism and the iOS side is live-confirmed,
I'd call the Android secure-context claim well-grounded, not merely hoped — but it is
explicitly not something I ran on this box, and the acceptance bar here is evidence over
opinion, so it stays marked unverified until someone with an Android emulator or device
confirms it.

## Storage: the AMK's lifetime in a WebView

**Real finding, not covered by the issue's original framing, and worth its own issue
(filed as #950).**

`amk-store.ts`'s own doc comment already accepts a real limitation for the browser case:
the AMK persists in `localStorage`, never uploaded anywhere, no recovery path if that
storage is cleared. That's a reasonable trade for a desktop/mobile **browser tab** — no
desktop or mobile browser sweeps a site's `localStorage` into an OS-level cloud backup by
default.

A Capacitor-wrapped app is a different threat model, and I verified the concrete mechanism
on both platforms rather than assuming it:

- **Android**: the real `cap add android` output above generates
  `android:allowBackup="true"` — Capacitor's own default. Android's Auto Backup includes
  the app's private data directory by default when that flag is true (Android's own docs:
  "all of the data files of an app are automatically copied to a user's Drive… up to 25 MB
  per app"), and WebView `localStorage`/IndexedDB lives inside that directory
  (`app_webview/Default/Local Storage/` on modern Chromium-based WebView). An AMK persisted
  there would, by default, ride along into the user's Google account backup.
- **iOS**: WKWebView's storage lives under the app's `Library` directory, and per Apple's
  own guidance everything under `Library` (excluding only `Caches`/`tmp`) is included in
  iCloud/iTunes backups by default unless explicitly marked with
  `NSURLIsExcludedFromBackupKey`. Same exposure, different mechanism, same platform-default
  answer: included unless the app opts out.

Neither is mitigated anywhere in this spike's scaffold, because this spike doesn't persist
a real AMK — the diagnostics page only round-trips a throwaway test key
(`__loombox_diag__`) to prove `localStorage` itself works, which it does on both the
iOS-verified run and locally. The gap only matters once the real v3 mobile phase wires the
actual PWA (and therefore `loadOrCreateAmk`) into the wrap, but it needs to be closed
*before* that, not discovered after. #950 has the concrete fix options (disable/scope Auto
Backup on Android and mark the WebView data directory excluded on iOS, or move the AMK into
Keychain/Keystore via a Capacitor plugin per Capacitor's own security guide's "use secure
keychain/keystore techniques" recommendation for persisted sensitive values).

Aside from the backup question, a WebView's `localStorage` is otherwise **more** durable
than a shared desktop browser's: it's a single dedicated app profile with no other
origins competing for it, so none of a general-purpose browser's own storage-pressure
eviction heuristics for rarely-used sites apply. The lifetime concern here is specifically
the backup channel, not everyday persistence.

## The relay connection: WebSocket from a WebView, and app suspend

**Live-verified that a WebView can hold a real WebSocket open and round-trip data** (the
same iOS screenshot above: `PASS — WebSocket round trip: open + echoed …`). The remaining
question — what a suspend/background transition does to it — I answered by reading
Capacitor's own lifecycle source rather than by inducing a real backgrounding cycle on the
Mac over SSH (no reliable way to drive "send the simulator to the background and wait" and
observe the result headless).

`BridgeActivity.java`'s `onPause()`/`onStop()` and `Bridge.java`'s corresponding methods
forward the Android lifecycle **only to registered plugins**
(`plugin.getInstance().handleOnPause()` etc.) — grep'd the whole file, there is no call to
`webView.onPause()` or `webView.pauseTimers()` anywhere in Capacitor's own bridge. That
matters because `WebView.onPause()`/`pauseTimers()` is the actual Android API that freezes
JS timers; Capacitor deliberately doesn't invoke it. So on Android, the relay's JS timers
(reconnect backoff, the 30 s heartbeat) keep running while backgrounded, for as long as the
OS keeps the process alive — Android's own Doze/App Standby eventually throttles network
and CPU for backgrounded apps, and the process can be reclaimed under memory pressure with
no guaranteed grace period, but there's no Capacitor-specific freeze on top of that.

iOS is stricter, and this is Apple's own documented (if informally, since exact timing is
deliberately undocumented) behavior, not a Capacitor choice: **WKWebView JS execution is
suspended, not merely throttled, within roughly 30 seconds of backgrounding**, by design —
"any app that is suspended no longer gets to execute code" (Apple engineer, Apple Developer
Forums; corroborated by the WebKit team's own open radar on the same behavior). So on iOS,
any open WebSocket is left exactly where it was the instant JS stops, until the app returns
to the foreground.

**Neither platform needs new reconnect logic to recover** — `relay-client.ts` already
treats a stale/half-open connection as first-class: `heartbeatIntervalMs` (30 s) pings a
relay that advertises heartbeat capability and force-closes if the pong doesn't arrive by
the next tick, and `scheduleReconnect` retries with backoff from `initialBackoffMs` (250
ms) up to `maxBackoffMs` (10 s) on any unexpected close. Worst case on resume: up to one
heartbeat interval (30 s) before the staleness is even detected, plus the reconnect itself
— call it under a minute, self-healing, no code change required to *not break*.

**Named recommendation, not a blocker**: wire `@capacitor/app`'s documented `resume` event
(`App.addListener('resume', () => relayClient.connect())`, `connect()` already being a
safe no-op-if-connected re-arm per its own doc comment) to force an immediate reconnect
check the instant the app returns to the foreground, instead of waiting out that up-to-30s
heartbeat-miss window. Small, concrete, and the same shape as the reconnect-with-backoff
work the desktop app already got for issue #511.

## What I did not verify, and why

- **Android runtime** (`isSecureContext`, `crypto.subtle`, `localStorage`, live WebSocket)
  — no emulator or system images on this devbox (confirmed: `~/android` has build-tools,
  platforms, platform-tools, ndk, cmake; no `emulator` package). Grounded in Capacitor's
  own Android source instead (see above); genuinely unverified at runtime, not assumed to
  be fine.
- **The real loombox PWA booting inside either wrap** — this spike's `webDir` is the
  diagnostics probe, not `apps/web`'s build output, for the reason in "Does the build work
  at all" above. Once the static-build-target follow-up lands, re-running this exact spike
  process against the real build is the natural next check.
- **A real backgrounding/resume cycle observed end to end** — reasoned from Capacitor's and
  Apple's own documented lifecycle behavior (cited above), not induced and watched live on
  the simulator; there was no reliable headless way to trigger "send to background, wait,
  bring to foreground" over SSH and capture the WebSocket's state through that transition.
- **Android's Auto Backup actually copying `localStorage` into a Drive backup** — grounded
  in the real generated `android:allowBackup="true"` default plus Android's own documented
  Auto Backup scope, not observed through an actual backup/restore cycle (this spike never
  persists a real AMK, so there's nothing sensitive to observe leaking in the first place).

## Recommendation

**Proceed** with the Capacitor-wrap architecture SPEC/AGENTS.md already committed to — the
core risk (is this a secure context at all) came back positive on the platform I could
verify live, and is well-grounded on the one I couldn't. Three named changes before the
real v3 mobile epic (#34) builds product on this scaffold, in rough priority order:

1. **Give the PWA a maintained static-SPA build target** (adapter-static + `ssr = false`,
   proven to build cleanly above) so `cap sync` has the real app to bundle, not this spike's
   diagnostics stand-in.
2. **Close the AMK-backup gap on both platforms before ever persisting a real AMK in the
   wrap** (#950) — this is the one item that would be a genuine regression versus the
   browser-only PWA's threat model if shipped as-is.
3. **Wire `@capacitor/app`'s `resume` event to force an immediate relay reconnect check**
   (this doc's WebSocket section) — quality-of-life, not correctness, since the existing
   heartbeat/backoff design already self-heals within about a minute.

Plus the small, non-blocking build-tooling note: pin JDK 21 for `apps/mobile`'s Android
build (#951).
