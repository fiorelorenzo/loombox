# loombox IA v4 — design spec ("projects are real, one navigation, one place per thing")

Status: agreed with Lorenzo (2026-07-25). Follows
`docs/superpowers/specs/2026-07-25-redesign-v3-design.md` (#504), which merged the rail
and the sessions column into one sidebar and re-art-directed the surface. v3 fixed how the
shell *looks*. This spec fixes what it *is*: v3 left two navigations pointing at the same
destinations, and left `Project` as a string on a session rather than the first-class
concept SPEC §6 defines.

Unlike v3, this is not purely a client change. Two of the three problems below are gaps
between SPEC and the code, and they are closed here.

## 1. What is actually wrong

### 1.1 The same navigation exists twice

`+page.svelte:1987-2030` renders sidebar nav rows for Inbox / Nodes & targets / Settings.
`DRAWER_TABS` (`+page.svelte:203-210`) renders tabs for Inbox / Nodes & targets / Settings /
Files / Terminal / Config. Clicking the left one activates the right one. The same three
destinations are drawn twice on screen at the same time, and neither placement is where
they belong: a cross-project attention queue (SPEC §7.13) is a destination you go to, not a
slide-over you peek at.

### 1.2 `Project` does not exist

SPEC §6 defines it: "**Project** — any folder, local or remote. It does not have to be a git
repository." In the code it is `projectPath`, a string inside each session's encrypted
private envelope (`packages/protocol/src/v1/sessions.ts:24`). Consequences:

- A project cannot exist before its first session, so the working folder must be re-picked
  in the New session dialog every single time.
- Grouping in the sidebar is by *target* (`+page.svelte:1153`), not by project.
- The per-project config that already exists (`mcp-server-store.ts`, `plugin-store.ts`,
  `recent-paths.ts`) is keyed by a bare `projectPath` string with no owner.

### 1.3 Two SPEC violations block the flow Lorenzo asked for

- **The per-session worktree choice is unreachable.** SPEC §7.1: "if the folder is a git
  repo — whether to isolate in a new worktree or work in place ... The user chooses per
  session." The node implements it (`CreateNodeSessionOptions.worktree`,
  `node-daemon.ts:333`; worktrees at `<project>/.loombox/worktrees/<sessionId>` on branch
  `loombox/session-<sessionId>`, `session-manager.ts:196-198`), but `session_create` has no
  field for it, which that option's own doc comment admits at `node-daemon.ts:328-331`.
- **Non-git folders are rejected.** SPEC §6: "It does not have to be a git repository";
  SPEC §7.1: "Non-git folders are fully supported." `session-manager.ts:182` calls
  `assertIsGitRepo` unconditionally, including for `workInPlace` sessions, so any folder
  that is not a repo fails session creation outright.

## 2. Decisions made (with Lorenzo)

- **Sessions live in a tree in the sidebar**, nested under their project. Not emdash-style
  canvas tabs: session titles here are sentences, a 288px column reads them where an 18ch
  tab cannot; and attention dots must be visible across *all* projects at once, not only
  the active one.
- **Inbox / Nodes / Settings become pages in the main area**, not drawer tabs. The drawer
  keeps only what is scoped to the open session.
- **Full scope, protocol included.** Both SPEC gaps in §1.3 are closed in this change.

## 3. The target design

```
┌──────────────────────┬───────────────────────────────────────────┬─────────┐
│  ◈ loombox        ⇤  │  Refactor relay routing      ⌘K ▤ ▶ ⚙     │         │
│                      ├───────────────────────────────────────────┤ session │
│  ▣  Inbox         3  │                                           │workbench│
│  ⬡  Nodes            │              transcript                   │ (Files, │
│  ⚙  Settings         │                 or                        │Terminal,│
│  ────────────────    │             a full page                   │ Config) │
│  PROJECTS         +  │                                           │         │
│  ▾ loombox      2 ●  │                                           │         │
│      ● Refactor…     │                                           │         │
│      ○ Fix crypto    │                                           │         │
│      + New session   │                                           │         │
│  ▸ pitchbox          │                                           │         │
│  ────────────────    │                                           │         │
│  ⬤ Lorenzo        ⋯  │                                           │         │
└──────────────────────┴───────────────────────────────────────────┴─────────┘
```

The organising rule, which every question below resolves against: **the left column is
where you are, the right drawer is what you are working on.** A surface that is not scoped
to one open session may not live in the drawer.

### 3.1 Sidebar

Top to bottom, replacing today's order:

1. **Brand row** — unchanged (`BrandMark` + wordmark + collapse toggle).
2. **Primary destinations** — Inbox (count badge), Nodes (health dot), Settings. These are
   the "bigger" rows Lorenzo asked for: 40px tall, 20px icon, `--text-body` label, not
   today's 32px muted `--text-small` rows. Active state is a filled surface, because these
   now indicate *what the main area is showing*, which is a stronger claim than a toggle.
3. **Divider.**
4. **`PROJECTS` section header** with a trailing `+` `IconButton` (Add project).
5. **The project tree** — see 3.2.
6. **Spacer**, then the **account row**, unchanged from v3.

The `New session` split button is **removed from the sidebar**. It is not a global action:
every session belongs to a project, so its entry points are all project-scoped (3.4).
`Add target` / `Connect a node`, which the split menu also carried, move to the Nodes page,
where they are one-time setup actions among their own kind.

### 3.2 The project tree

Each project is a collapsible group:

```
▾ loombox                    2 ●
    ● Refactor relay routing   2m
    ○ Fix the crypto base64    1h
    + New session
▸ pitchbox                     ●
```

- **Group header**: chevron, project name, and on the right the count of sessions needing
  attention plus a single `StatusDot` at the project's worst live status. Hover reveals a
  `⋯` menu: New session, Rename, Reveal path, Remove project.
- Expanded/collapsed state is per project and persisted (same treatment as v3's group
  collapse, which was transient — this one survives a reload, since a project you never use
  should stay shut).
- **Session rows** keep v3's §3.2 anatomy verbatim (`StatusDot`, title, meta line, hover
  `⋯`), indented one step. The meta line drops the project name, which the group header now
  carries, and shows `target · relative time` instead.
- The last child of an expanded group is a quiet **`+ New session`** row. This is the
  primary creation affordance, and it carries its project as context.
- **Removing a project never touches its sessions**: it removes the registry entry only,
  after which the project reappears as an adopted entry if any of its sessions still exist
  (see 4.2). Removal is for pruning stale folders, not for deleting work; the menu item says
  so.

The existing session **filter input** stays, above the tree, and now matches on project name
as well as title/target. A non-empty filter auto-expands every group with a match.

### 3.3 Main area

`mainView: 'session' | 'inbox' | 'nodes' | 'settings'`.

- Selecting a session sets `'session'`. Selecting a destination sets that destination and
  **leaves the session selected** in the sidebar, so returning is one click and the header
  breadcrumb is never lost.
- The three pages are full-width surfaces with the same measure rule as the transcript
  (`max-width: var(--measure-wide)`, centred), a page title, and no close button — you leave
  a page by going somewhere else, which is what the sidebar is for.
- **Empty state** (no session selected, `mainView === 'session'`): this is where the primary
  `New session` CTA now lives, per Lorenzo. With no projects registered at all it instead
  offers `Add project`, and with no targets connected, `Connect a node`. One CTA at a time,
  always the one that unblocks the next step.

### 3.4 Session creation, split in two

Today one dialog asks for target, provider, folder, title and prompt on every creation. The
folder is a property of the project, not of the session, so it is asked once:

| | Add project (once per folder) | New session (every time) |
|---|---|---|
| Target | picked | inherited, shown read-only |
| Folder | `DirectoryPicker` | inherited, shown read-only |
| Name | editable, defaults to basename | — |
| Agent | — | `Select` (provider) |
| Worktree | — | toggle, **only when the folder is a git repo** |
| Title, prompt | — | as today |

Entry points for New session: the `+ New session` tree row, the project group's `⋯` menu,
the main-area empty state, and ⌘K. Every one of them passes a project; there is no
project-less creation path.

The worktree control is a two-option choice, not a bare checkbox, because the two outcomes
are not "on/off" but two different places the agent will write:

- **Isolated worktree** (default when the folder is a git repo) — "a fresh branch
  `loombox/session-<id>` under `.loombox/worktrees/`, so several agents can work on this
  project at once."
- **In place** — "directly in the project folder. Only one session at a time can do this."
  That second sentence is SPEC §7.2's same-folder rule, stated where it applies rather than
  discovered as an error later.

When the folder is not a git repo the control is absent and the session works in place.

### 3.5 Drawer

Reduced to the session's own workbench: **Files, Terminal, Config**. Inbox / Nodes /
Settings leave `DRAWER_TABS` entirely. Everything else about the drawer (pinning, the
overlay/bottom-sheet breakpoints, the tab strip's visuals) is unchanged from v3 §3.6.

With three tabs the strip no longer needs horizontal scrolling at any supported width, but
the scroll behaviour stays rather than being re-litigated.

### 3.6 Header

Unchanged from v3 §3.3, with one addition: the breadcrumb reads `project · target` using
the project's **name** where one is registered, falling back to the path basename. When
`mainView !== 'session'` the header shows the page title in place of the breadcrumb and
hides the session-scoped `IconButton`s.

## 4. Contracts

These are fixed before any slice starts and are the only interfaces between them.

### 4.1 Protocol (`packages/protocol`)

Both additions are **optional fields**, so a node or client older than its peer keeps
parsing. Tonight's relay incident is the reason this is stated as a rule: the relay drops
frames that fail validation and never reports a version mismatch, so a required field added
on one side silently breaks the other.

```ts
// v1/sessions.ts — the plaintext inside a session's private envelope.
// Replaces the interface duplicated in node-daemon.ts:337 and relay-client.ts.
export const sessionPrivateMetaV1 = z.object({
  title: z.string(),
  projectPath: z.string(),
  /** SPEC §7.1's per-session choice. Omitted = the target kind's default. */
  worktree: z.boolean().optional(),
});
```

```ts
// v1/target-fs.ts — targetFsListResultV1 gains:
  /** Whether `path` is inside a git work tree, so the client knows whether to
   *  offer SPEC §7.1's worktree choice. Optional: an older node omits it and
   *  the client treats that as "unknown". */
  gitRepo: z.boolean().optional(),
```

`PROTOCOL_VERSION` does not change: both are backward-compatible additions.

### 4.2 The project registry (`apps/web/src/lib/projects.ts`)

New module, following `recent-paths.ts` / `mcp-server-store.ts` exactly: `localStorage`
under `loombox:projects`, storage injected as a constructor parameter with a real-browser
default, unit-testable in the `node` vitest environment without jsdom.

```ts
export interface Project {
  id: string;          // uuid
  name: string;        // display name; defaults to the path's basename
  nodeId: string;
  targetId: string;
  path: string;        // absolute, on that target
  isGitRepo?: boolean; // learned from the fs listing; undefined = not yet known
  createdAt: number;
}
/** `${nodeId}:${targetId}:${path}` — the identity of a project, since the same
 *  path on two targets is two different projects. */
export function projectKey(p: Pick<Project, 'nodeId' | 'targetId' | 'path'>): string;
export function sessionProjectKey(s: ClientSessionMeta): string;
export function createProjectStore(storage?: ProjectStorage): ProjectStore;
```

`ProjectStore` is a Svelte `Readable<Project[]>` plus `add`, `rename`, `remove`,
`setGitRepo`, and:

```ts
/** Registers a project for every (nodeId, targetId, projectPath) triple present
 *  in `sessions` that has no entry yet, so existing sessions never appear
 *  orphaned and an upgrade from v3 shows a populated tree on first load.
 *  Never removes anything. Idempotent. */
adoptFromSessions(sessions: ClientSessionMeta[]): void;
```

Account-wide sync of this registry through the relay is deliberately **out of scope** and
filed separately, matching the identical decision already documented in
`mcp-server-store.ts`'s header. Until then the registry is per-device, and
`adoptFromSessions` means a new device still sees every project that has sessions.

### 4.3 Component boundaries

- The pages slice creates `InboxPage` / `NodesPage` / `SettingsPage` whose props are
  **exactly** the props today's drawer panels receive, so the shell swaps the component name
  and leaves the prop expressions untouched.
- The dialogs slice owns `AddProjectDialog` (new) and `NewSessionDialog` (rewritten). Both
  are pure: they never touch the project store, they call
  `onCreated(...)` and let the shell commit.
- Only the shell slice edits `+page.svelte`.

## 5. Out of scope

Relay-backed project sync; real SvelteKit routes for the three pages (`mainView` is state
for now, deep links stay session-only); the board/list view of SPEC §7.2; pin/tag/archive;
project-level provider defaults; any change to the crypto boundary.
