A Realtime voice transport

A1

Where a realtime voice session's audio socket lives

Not urgent

#277's design (docs/superpowers/specs/2026-08-08-voice-backend-design.md, "Who talks to the vendor" section) already settles who holds a BYO vendor key: the node, always, the same rule SPEC §8 already gives SSH credentials and connected accounts ("held per node/target, not shared through the relay"). A client never sees the raw ElevenLabs key. That is not this decision. This decision only exists for a genuinely realtime, duplex backend — SPEC §7.12 names "a realtime API" as a second backend shape alongside ElevenLabs — because a live, bidirectional audio session cannot be proxied for free the way a request/response call can.

Both vendors #277 checked while writing that design build the same escape hatch into their realtime products. ElevenLabs' streaming TTS WebSocket accepts either the real xi-api-key header or a single_use_token minted separately, "recommended for client-side access to avoid exposing your API key" (elevenlabs.io/docs/api-reference/text-to-speech/…/stream-input); its realtime Scribe STT endpoint takes the same shape, "an alternative to API key or bearer token authentication for frontend clients," a token from POST /v1/single-use-token/batch_scribe that expires after 15 minutes (elevenlabs.io/docs/api-reference/speech-to-text/convert). OpenAI's Realtime API mirrors it: a standard bearer key for a server-to-server socket, or a short-lived ephemeral client token "when the connection needs to originate from a browser/mobile device directly" (developers.openai.com/api/docs/guides/realtime-websocket). Every realtime-shaped vendor checked here has already built the same two doors.

TodayNo realtime backend exists, so this decision has zero effect on anything currently open

#278 and #279 are both turn-based only — a complete recorded clip in, a complete synthesized reply out, using ElevenLabs' batch POST /v1/text-to-speech/{voice_id} and POST /v1/speech-to-text, never a socket. The VoiceBackend interface #277 sketched has an optional connect(): Promise<VoiceRealtimeSession>, but it is typed undefined for ElevenLabs and for the local stub — nothing in the v3 epic calls it. This is genuinely a decision about a backend nobody has proposed yet, not a blocker hiding inside #278/#279.

A1-1Always proxied through the node (the design's own default)

Buys: one trust model for every backend shape, with no new exception to "a vendor only ever sees the node, never a client's IP" — the same guarantee SSH credentials already have under SPEC §8. Nothing about the mobile client (#278/#279's Android/iOS work already ships) needs to change either: it already talks only to the relay. Costs: real added latency per audio frame, for a product category whose entire value proposition is sub-200ms turnaround — loombox's own relay/session fan-out becomes the bottleneck for the one feature that exists specifically to avoid one.

A1-2Node mints a vendor ephemeral token, client connects to the vendor directly for the live duplex only

Buys: the actual latency a realtime backend is for. The raw BYO key still never leaves the node under this option — only a vendor-minted, single-purpose, time-boxed token does (15 minutes for ElevenLabs' Scribe token, per its own docs above). Costs: for the lifetime of that one session, the vendor sees the client device's real IP directly and can correlate its own timing/volume metadata with it — a real, if narrowly scoped (one vendor, one live session, token-expiring) new category of exception to "no third party ever sees anything about the user except through the node."

Not urgent: nothing currently open needs this pick, and it is safe to leave unanswered — #278/#279 build the same way either way. It is listed because #277 asked that it not get lost before a real duplex backend is proposed, and because it is a genuine latency-vs-key-custody trade with no vendor-mandated right answer: both ElevenLabs and OpenAI support either shape, so this is a loombox trust-model call, not a platform constraint. If you'd rather decide it now than have it resurface later, A1-1 is the safer default to bank until then — it's what #277's design already assumes.

B Voice-approval scope

B1

Does voice ever resolve an "always"-kind permission option

Urgent — blocks #280

Every pending permission request already carries its own options[], each tagged kind: 'allow_once' | 'allow_always' | 'reject_once' | 'reject_always' (AcpPermissionOption, packages/providers/core/src/types.ts:154-161), and the client resolves one by sending back its optionId as a PermissionResponse.decision over the exact same wire message a tap or a keyboard digit already uses (permissionResponse, packages/protocol/src/v1/steering.ts:44-51). #280's own acceptance criteria require voice to resolve that same decision, not invent a second permission model. The two live provider adapters' real fixtures show what "every kind" actually contains: Claude's set includes Allow once (once) alongside Allow all edits, Bypass everything, and Allow for this session (all allow_always — providers/claude/src/permissions.test.ts:9-13); Codex's is narrower — Allow Once, Allow for Session (allow_always), Reject (providers/codex/src/permissions.test.ts:15-17), though its execpolicy-amendment flow adds standing network/command grants of its own (:65-77). allow_always/bypass-kind options grant standing access beyond the one tool call currently on screen — a misheard "always" is a plausible STT failure mode, not a hypothetical one, and it has a materially worse blast radius than a misheard "once", which only ever affects one already-visible tool call.

TodayThe keyboard/tap path already resolves every kind equally, and nothing about voice exists yet

A tap or a 1..n keystroke on a focused permission card sends whichever optionId it points at, allow_always/bypass included, with no extra gate today. Voice would be the first time speech, not a deliberate physical action, can reach that same standing-grant outcome.

B1-1Restrict voice to *_once kinds only

An allow_always/reject_always-shaped option, if the request offers one, is never voice-resolvable — it falls through to "unrecognized" and stays queued for a tap. Buys: the single highest-consequence class of permission decision (a standing grant like Claude's own Bypass everything) can never be issued by a misheard word, full stop. Costs: a genuinely deliberate, correctly-recognized "always" spoken command still has to be tapped instead — friction #280 never asked for, on the case that is least likely to be the misrecognition.

B1-2Allow every kind the request offers, gated only by a confidence floor

Buys: full parity with the keyboard-shortcut path, which is #280's own stated bar — "exactly as the existing 1..n keyboard-shortcut path does." No option kind is ever structurally out of reach for voice. Costs: the confidence floor becomes the only thing standing between a misheard word and a standing grant, and there is no recognition-accuracy data yet — from ElevenLabs' STT or from real usage — to set that floor responsibly. #277's design explicitly declined to bake a number in for exactly this reason.

B1-3B1-2, plus a spoken re-confirmation step before an "always"/"bypass" decision commits

Not one of #277's own two options — a synthesis of its third recommendation (any destructive-shaped decision gets an audible read-back via VoiceBackend.synthesize() before or immediately after committing, "Approved: allow once" or similar) applied specifically to the always/bypass kinds, as a second utterance rather than a passive announcement. Buys: most of B1-2's parity while adding a deliberate second gate on exactly the decisions B1-1 worries about, closer to a two-step confirmation than either pure option gives you. Costs: new interaction surface #280 was not scoped to build (a second listen-and-match cycle, its own confidence floor, its own timeout-and-fall-through behavior), and it does not structurally close the risk B1-1 closes — a second misheard "yes" still resolves the confirmation, it only narrows the window.

No clean technical answer here — this is a real security/UX trade-off, not a platform constraint either vendor forces. #280 is otherwise ready to build; it is blocked specifically on this pick, per #277's design ("this one is urgent for #280 specifically and should be settled before that issue's implementation, not after"). If you don't have recognition-accuracy numbers you trust yet, B1-1 is the option that stays safe without them.

C Store identity

C1

Whose identity signs and lists loombox in each store

Urgent — blocks #283's own acceptance

Neither store account exists yet. This repo's own facts point one way today: the GitHub owner is fiorelorenzo, a personal account, not an organisation; LICENSE reads "Copyright (c) 2026 Lorenzo Fiore", one person, not a company; and SPEC only ever mentions loombox-the-company as a hypothetical operator of a possible future managed-cloud edition, explicitly gated "well past v1" and deferred past v3 (SPEC §12, §17.1). No legal entity exists for loombox to enroll as, today, even if you wanted to. apps/mobile's Capacitor appId is already dev.loombox.app (apps/mobile/capacitor.config.ts) — a reverse-DNS identifier, unaffected by which account type eventually signs it.

Both stores draw the same line, and both cite the same underlying reason: an organisation account requires a real, verifiable legal entity. Apple: "Individuals or sole proprietors/single-person businesses. Apps are listed under the developer's personal name" versus "Organizations. Apps are listed under the organization's legal entity name. Companies and educational institutions must provide a D-U-N-S Number (available for free) registered to their legal entity" (developer.apple.com/support/compare-memberships). Apple is explicit that it will not accept a stand-in for that entity: "Apple does not accept DBAs, fictitious businesses, trade names, or branches for enrollment as a company/organization" (developer.apple.com/help/account/membership/D-U-N-S). Google Play draws the identical line: "To create a developer account for an organization, you must have a D-U-N-S number," while a personal account needs only "a private email address and phone number... and a developer email address," with no entity or D-U-N-S involved (support.google.com/googleplay/android-developer/answer/13634885). Neither store's fee differs by account type: Apple is 99 USD/year either way (compare-memberships, above); Google is a 25 USD one-time registration fee either way (support.google.com/googleplay/android-developer/answer/6112435, "Step 3: Pay registration fee ... US$25 one-time registration fee").

TodayNo Apple Developer Program or Google Play Console account exists for loombox at all

#283 is otherwise ready to build: a signed build/release pipeline can be scripted and verified against a throwaway or personal account today. Only the actual store listing — the part of #283's acceptance criteria that needs a real, permanent account identity — is blocked on this pick.

C1-1Individual/personal accounts, under Lorenzo Fiore

Buys: enrollable today, with nothing but your own identity — no D-U-N-S number, no legal-entity paperwork, no business registration — which matches loombox's actual legal status right now exactly (one person, no company, per LICENSE and SPEC §12/§17.1 above). Costs: Apple lists every app "under the developer's personal name," and moving the Account Holder role off an individual account later is not a normal operation — Apple's own docs restrict it to "when a minor reaches the age of majority... or when the Account Holder is deceased," requiring Apple Developer Support's direct assistance either way (developer.apple.com/help/account/access/transfer-the-account-holder-role). There is structurally no "hand this to a future company" path from an individual account — only opening a brand-new organisation enrollment and re-signing/re-provisioning both app listings under it, which is precisely the "hard to change later" #283 itself names.

C1-2Organisation accounts, under a loombox legal entity

Buys: apps ship under a real legal entity's name from day one, and the Account Holder role can later move to any team member "who has the legal authority to bind your organization to legal agreements" — a normal operation, not a support-only exception (Apple, above). This is the option that actually solves #283's "hard to change later" framing, permanently. Costs: it needs a D-U-N-S number and a legal entity Apple/Google will accept as real — neither exists for loombox today, and forming one is a legal and financial decision an app store enrollment form cannot make for you. This option is blocked on that step happening first; it is not a checkbox you can tick at signup.

C1-3Ship #283's pipeline now under C1-1, hold the actual store listing until a legal entity exists

Buys: never pays C1-1's transfer cost, because nothing is ever listed under a personal name to begin with — when/if a company forms, the very first listing is already the organisation's. #283's own acceptance criteria (a documented, scripted, signed .ipa/.aab build, and Changesets covering apps/mobile version bumps) do not require a live store listing to verify — Apple's compare-memberships page lists "App management, testing, and analytics with App Store Connect" as included in the Apple Developer Program regardless of account type, and Google Play's testing/internal distribution tracks work the same way under a personal account. Costs: "shippable rather than a dev-only spike" — #283's own framing — stays half true: buildable and signable, not actually reachable by a real user through either store, for as long as the entity question stays open. That is a real cost if "get this in front of a beta user soon" matters more than avoiding the C1-1 transfer friction.

There is a real technical constraint right now, not just a preference: C1-2 is not actually available today — there is no legal entity for either store to verify, so picking it means picking "form a company first," which is a decision far bigger than an app-store enrollment form and outside what this artifact can settle for you. The genuinely open question is C1-1 vs. C1-3: enroll as yourself now and accept the one-way transfer cost if you ever incorporate, or delay the store listing specifically (not the rest of #283) until that question is settled on its own terms.
