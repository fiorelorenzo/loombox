A1

Where a realtime voice session's audio socket lives

Not urgent

#277's design (docs/superpowers/specs/2026-08-08-voice-backend-design.md, "Who talks to the vendor" section) already settles who holds a BYO vendor key: the node, always, the same rule SPEC §8 already gives SSH credentials and connected accounts ("held per node/target, not shared through the relay"). A client never sees the raw ElevenLabs key. That is not this decision. This decision only exists for a genuinely realtime, duplex backend — SPEC §7.12 names "a realtime API" as a second backend shape alongside ElevenLabs — because a live, bidirectional audio session cannot be proxied for free the way a request/response call can.

Both vendors #277 checked while writing that design build the same escape hatch into their realtime products. ElevenLabs' streaming TTS WebSocket accepts either the real xi-api-key header or a single_use_token minted separately, "recommended for client-side access to avoid exposing your API key" (elevenlabs.io/docs/api-reference/text-to-speech/…/stream-input); its realtime Scribe STT endpoint takes the same shape, "an alternative to API key or bearer token authentication for frontend clients," a token from POST /v1/single-use-token/batch_scribe that expires after 15 minutes (elevenlabs.io/docs/api-reference/speech-to-text/convert). OpenAI's Realtime API mirrors it: a standard bearer key for a server-to-server socket, or a short-lived ephemeral client token "when the connection needs to originate from a browser/mobile device directly" (developers.openai.com/api/docs/guides/realtime-websocket). Every realtime-shaped vendor checked here has already built the same two doors.

TodayNo realtime backend exists, so this decision has zero effect on anything currently open

#278 and #279 are both turn-based only — a complete recorded clip in, a complete synthesized reply out, using ElevenLabs' batch POST /v1/text-to-speech/{voice_id} and POST /v1/speech-to-text, never a socket. The VoiceBackend interface #277 sketched has an optional connect(): Promise<VoiceRealtimeSession>, but it is typed undefined for ElevenLabs and for the local stub — nothing in the v3 epic calls it. This is genuinely a decision about a backend nobody has proposed yet, not a blocker hiding inside #278/#279.

A1-1Always proxied through the node (the design's own default)

Buys: one trust model for every backend shape, with no new exception to "a vendor only ever sees the node, never a client's IP" — the same guarantee SSH credentials already have under SPEC §8. Nothing about the mobile client (#278/#279's Android/iOS work already ships) needs to change either: it already talks only to the relay. Costs: real added latency per audio frame, for a product category whose entire value proposition is sub-200ms turnaround — loombox's own relay/session fan-out becomes the bottleneck for the one feature that exists specifically to avoid one.

A1-2Node mints a vendor ephemeral token, client connects to the vendor directly for the live duplex only

Buys: the actual latency a realtime backend is for. The raw BYO key still never leaves the node under this option — only a vendor-minted, single-purpose, time-boxed token does (15 minutes for ElevenLabs' Scribe token, per its own docs above). Costs: for the lifetime of that one session, the vendor sees the client device's real IP directly and can correlate its own timing/volume metadata with it — a real, if narrowly scoped (one vendor, one live session, token-expiring) new category of exception to "no third party ever sees anything about the user except through the node."

Not urgent: nothing currently open needs this pick, and it is safe to leave unanswered — #278/#279 build the same way either way. It is listed because #277 asked that it not get lost before a real duplex backend is proposed, and because it is a genuine latency-vs-key-custody trade with no vendor-mandated right answer: both ElevenLabs and OpenAI support either shape, so this is a loombox trust-model call, not a platform constraint. If you'd rather decide it now than have it resurface later, A1-1 is the safer default to bank until then — it's what #277's design already assumes.
