Where the latency goes, and what's actually measured

Lorenzo's question was how close a PWA can get to Zed feeling "super reattivo e veloce". This table lays out where each side's time actually goes, and every row is labelled by what kind of claim it is: published is a number Zed states about itself, not verified against a running loombox build here; mechanism is what this repo's code actually does, cited to a line; derived is arithmetic run against loombox's own shipped constants, not a stopwatch on a real burst. Nothing below was benchmarked end to end: no profiler was attached to either app for this artifact. Read every "not measured" row as exactly that, an open question, not a claimed win or loss.

E1

The transcript's DOM: keep everything mounted, or window it

Today <ol class="items"> (+page.svelte:3433-3437) renders every item in transcript.items, keyed by id, no cap: {#each transcript?.items ?? [] as item, itemIndex (item.id)} (:3439). Nothing in the app uses content-visibility or contain-intrinsic-size, grepped the whole of apps/web/src, zero hits. A session that has run for hours pays the DOM, layout and paint cost of every turn it ever had, on a phone exactly as much as on a desktop. The behaviour that actually rides on this: while following, an $effect re-reads el.scrollHeight and sets el.scrollTop = el.scrollHeight every time the transcript changes (:2228-2234), scrolling away drops followingTranscript past a 48px slack (:2202, :2208-2211), and jumpToLatest (:2213-2215) re-attaches. scrollHeight is only trustworthy if every item's real height is already known, which today it always is, because every item is mounted.

Today Every item mounted, no cap

Simplest code: scrollHeight is exact because every item's real height is already laid out, so scroll-to-bottom-while-streaming is one line, el.scrollTop = el.scrollHeight, correct on the first try. Costs a DOM, layout and paint bill that only grows across a session's life, paid in full even while scrolled away reading something else.

E1-1 Keep, and accept it

Zero engineering, zero regression risk. Scroll-to-bottom-while-streaming stays exactly Today's one-liner, exactly as long as that stays fast enough. Buys nothing new; costs a session that gets slower to scroll, type in and switch away from the longer it runs, worse on a phone than a desktop.

E1-2 content-visibility: auto per item

A handful of CSS lines per item: content-visibility: auto plus a contain-intrinsic-size guess skip layout and paint for whatever's off-screen while every item stays mounted, findable and anchorable. Scroll-to-bottom-while-streaming stays the same one line, and scrollHeight stays exact for it in the case that matters most: a new item appears at the bottom of a session you're already following, so it's on-screen at least once and its real height gets remembered from then on. Costs an approximate scrollHeight for the rest of the session, the part nobody has scrolled to yet.

E1-3 Real windowing

Mount only the visible range: the fastest of the four, since an unmounted item costs nothing at all, not even a skipped-layout box. Scroll-to-bottom-while-streaming stops being one line: the virtualizer's own estimated total height shifts every time an off-screen item's real height finally gets measured, so "stay pinned to the bottom while streaming" needs the same active anchoring every virtualization library ships a dedicated mode for. It also breaks native browser find and any anchor link into one item, since no transcript item even carries a DOM id today (grepped, no match) and windowing would leave that permanently true. Read #203 and #263 before citing this against search specifically: the planned transcript search is designed to run against the underlying event model, not the DOM, and its own acceptance criteria already require matching virtualized-but-unmounted items, so windowing does not cost that one feature, contrary to the obvious assumption.

E1-4 content-visibility now, windowing if measurement says so

Ships E1-2's win today, keeps every cost E1-3 would add (native find, anchor links, the harder scroll-to-bottom math) off the table until a real session proves content-visibility isn't enough. Scroll-to-bottom-while-streaming behaves exactly like E1-2, above, unless and until that measurement flips this to E1-3. Buys the cheap win now without pre-paying the expensive one's implementation cost; costs a second pass later if the measurement ever comes back negative, and nothing here supplies that measurement yet.

E2

Paced reveal: protecting against a burst, or against nothing

TextPacer reveals a live turn's text on a 32ms tick, at least 2 characters and up to 35% of the outstanding backlog per tick (text-pacer.ts:37-39, the constants; :112-125, the tick itself). It exists so a burst of chunks doesn't dump straight into the DOM and thrash it, per that file's own doc comment. But by the same formula's own arithmetic, a 2,000-character block that already fully decrypted and arrived in one setTarget call still takes about 16 ticks, roughly 512ms, to finish revealing on screen: derived here from the shipped constants, not measured against a real burst. That is the same shape of lag a slow network would produce, except this one is self-inflicted by the render layer, on an agent that answered instantly. Only a genuinely live turn paces at all; replayed history always renders in full the instant it mounts (MessageItem.svelte:22-31).

Today 32ms tick, 35% catch-up, no ceiling

Protects every burst size the same way, including sizes nobody has measured landing on a slow device. Costs exactly what the note above derives: a fast agent's answer visibly retypes for half a second, which reads as loombox being the slow part, not the agent.

E2-1 Keep as is

No change, no risk. Costs exactly Today's own note: a fast agent gets penalized by its own client for being fast.

E2-2 Raise the ceiling, name a tail budget

Keep the pacer, a real burst-thrash guard still exists, but raise how much of the backlog a tick can clear, tuned so the tail is never more than a stated number of milliseconds behind arrival, for example three ticks, 96ms. Buys back nearly all the perceived lag on a fast agent while keeping the original protection for a genuinely pathological burst. Costs a number to pick and defend: "never more than Nms" has to be checked against a real device, not just asserted.

E2-3 A preference: paced or immediate

Hands the trade to whoever is actually watching the screen. Buys a real off switch for anyone who wants terminal-like immediacy. Costs a second code path to keep correct (the turn_ended flush still has to work either way) and a setting nobody finds until they go looking for it, the same discoverability problem B2's "one global switch" argument already made.

E2-4 Adapt to the device: immediate on desktop, paced on phones

The burst-thrash risk this guards against is more a low-power CPU problem than a desktop one, so scope the protection to where it is actually needed. Buys a fast agent feeling instant on the machine most able to show it. Costs a device-class heuristic that has to be right: viewport width is a poor proxy for CPU class, a low-end tablet at desktop width would get the wrong answer, and now there are two behaviours to explain and test instead of one.

E3

Where decryption happens

Every envelope this client decrypts goes through one crypto.subtle.decrypt AES-256-GCM call, on the tab's main thread, one at a time. handleSessionUpdate (relay-client.ts:4137-4138) is one of a dozen handlers shaped exactly the same way, each awaiting its own openJson independently instead of collecting a burst first. The chain is openJson to decryptEnvelope to aesGcmDecrypt to crypto.subtle.decrypt (packages/crypto/src/aead.ts:68-85). The account's raw AMK lives as private readonly amk: Uint8Array on the RelayClient instance for the life of the tab (relay-client.ts:1034); getSessionKey derives each session's AES key from it once and caches the resulting CryptoKey (:4835-4842), imported extractable, not non-extractable (aead.ts:20-36's true argument). So a burst's real cost today is N serial subtle.decrypt calls on already-cached keys, not N key derivations.

Today Serial, main thread, no batching

Simplest code, one call-site shape reused a dozen times. Costs a burst of N envelopes being N sequential awaits on the same thread that is also laying out, painting and running Svelte effects.

E3-1 Keep

No change. Costs exactly what Today names, and it gets worse as the burst gets bigger.

E3-2 Batch a burst into one Promise.all

A small change: collect whatever has arrived on the socket in one microtask turn and decrypt it concurrently with Promise.all instead of one call after another. Buys most of the throughput win, since subtle.decrypt is already async and a browser can run several GCM operations at once, without moving a single byte of key material anywhere new. Costs staying on the main thread: a big enough burst can still visibly compete with a paint frame, and the win only shows up when messages actually arrive clustered, which a WebSocket does not guarantee.

E3-3 Move decryption into a Web Worker

Frees the main thread entirely: decrypt runs on its own thread, UI work never waits behind it. This is a real security question, not a pure performance one, so state it plainly. SPEC §8's whole model is about which network peer holds plaintext, device versus relay; it says nothing about isolation between two same-origin JS contexts inside one tab, and a Worker does not create the kind of boundary that stops an attacker who already runs code in this origin: same-origin script can already spawn its own worker or reach the one loombox creates. What does change: the AMK-derived key material now lives in two live JS heaps instead of one, whether the worker re-derives from a copied AMK or every derived session CryptoKey crosses a postMessage to reach it, a second file joins the small set of AMK-touching call sites an audit has to walk, and none of this even trades on non-extractability, since aead.ts already imports these keys extractable (:20-36). Buys the main thread back in full. Costs a second execution context to carry the account's key material through and review, for a boundary that does not actually stop the attacker SPEC §8 is worried about.

E3-4 Worker plus batching

Both changes stacked: Promise.all inside the worker's own message handler. Buys the full throughput win with the main thread fully clear. Costs both of the above at once, the worker's audit surface from E3-3 and the burst-timing dependency from E3-2, for the one option that actually earns "fastest" of the four.
