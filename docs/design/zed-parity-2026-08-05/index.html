How far do we go toward Zed?

You said Zed's UX is what you want, more dev-oriented than what we ship, and faster. This takes that apart into the decisions it actually implies: the look, the chrome, the thread, agents and MCP, speed, and the keyboard. Every decision shows what loombox does today, rebuilt from the current code, and two to four ways it could work instead.

Nothing here is built. The trade sentence on each option says what it costs, not only what it looks like. Where an option depends on plumbing we have not written, it says so in its first line. What needs no decision from you is already on the board.

How to answer

  1. Go through the decisions in order. Each has an id like C1.
  2. Pick one option per decision, by id: C1-2.
  3. If nothing fits, say so on that decision and what is missing. That is a useful answer, not a failure.
  4. Reply with just the list, for example A1-2, A2-1, A3-2, B1-1, ...

A1

The ground and the direction of layering

Today the dark theme runs rail #08090b, bg #0a0c0f, surface #0e1114, surface-raised #101418 (deck.css:30-33), all within 6 hex points of each other and at essentially zero chroma. The chrome (the rail) is the single darkest value in the set: chrome sits below the canvas, which sits below the cards. Zed's One Dark ground inverts that and adds real color: window #3b414d, panels #2f343e, editor #282c33, a blue-grey around hue 220° with roughly 10% saturation. The editor, the content well, is the deepest point; the chrome floats above it. That inversion plus the chroma is a large share of why Zed reads as a dedicated tool and loombox reads as a dark website. Borders and shadows are a separate question (A3); this is only about which surface is darkest and whether the palette has any hue in it.

A3

Borders, fills and elevation

Two different mechanisms are already in play today, and they don't have the same gap to Zed. Interactive state (hover/selected on a session row) is already a fill step, not a border change: hover is --color-fill-subtle (6% white), selected is --color-fill (12% white) (+page.svelte:4523-4529) — that part already matches Zed's own idiom. The real gap is the elevation ladder: Card.svelte maps flat to surface + a 9% white border and no shadow, raised to surface-raised + a 16% border and --shadow-sm, floating to surface-raised + a 28% border and --shadow-lg (Card.svelte:60-75). Borders are translucent everywhere, and there's a three-tier shadow scale used well beyond overlays: the composer carries --shadow-md (+page.svelte:5360-5362, settled by v7's A1-3, "the field sits on --color-surface-raised with a soft shadow... do not spread the shadow to other surfaces"), and PermissionCard carries --shadow-lg (PermissionCard.svelte:251-252). Zed uses opaque border colors, a fill step for hover/selected, and essentially no shadow outside a popover or a modal. Any option here that touches shadows has to reckon with the composer's shadow being an already-settled pick, not an open question.

A3-1Keep the hairlines and the shadow ladder

Zero migration risk, and it doesn't reopen v7's A1-3: the composer and PermissionCard keep exactly the lift they were given on purpose. Cost: this is precisely the softness Lorenzo pointed at when he said Zed reads more dev-oriented. Translucent borders and drop shadows read as a web app being careful about elevation; opaque borders read as a tool being precise about layout.

The base rule is code, kbd, pre, samp, .font-mono go monospace, described in typography.css:101-112 as covering "agent output, code, and diffs." In practice it already reaches further than that phrase suggests: project paths (ArchiveSessionDialog.svelte:108, NewSessionDialog.svelte:238), connected-account hostnames (ConnectedAccountsList.svelte:144), the terminal's cwd/shell/status (InteractiveTerminal.svelte:434-448), diff paths (DiffViewer.svelte:111,114), the file tree (FileTreePanel.svelte:249), the context-usage meter's numbers (ConfigBar.svelte:739, tabular figures per the doc comment at typography.css:22-26), and, already, the topbar's own project/target breadcrumb (+page.svelte:5031). D Agents & MCP

D1

Bringing your own ACP agent

Today the agent catalogue is a fixed, source-defined registry: RESERVED_PROVIDER_IDS names claude, codex, ohmypi, gemini, generic (provider-registry.ts:11), and only claude, codex and the test/ohmypi modules actually ship an adapter — gemini is a reserved id with no module yet. A session picks its provider once, at creation (node-daemon.ts:1264, provider: options.provider ?? 'claude'), and there is no code path anywhere in node-daemon.ts that changes a running session's provider afterward. Adding a new agent today means writing an AcpProviderModule and shipping it in a loombox release — never something a user does from the app. Zed's agent_servers setting is the opposite: any ACP binary by command + args + env, plus a default_mode and default_config_options, and Claude/Codex/Gemini are just entries of that same shape, not special-cased. The catch is that loombox's binary does not run in the browser tab — it runs on a node, which may itself be an ssh: target reached over a pooled transport (target.ts:6-15). "Add a custom agent" is therefore a remote-code-execution decision wearing a settings form, not a form validation problem.

TodayFixed registry, baked into the release

Only loombox's own commits can add a provider. Nobody, compromised or not, can point a session at an arbitrary binary — the safest possible answer, at the cost of the whole feature: no Gemini today, no in-house agent, no "point this at my own ACP wrapper" without a release.

D1-1Custom agents live in the node's own config, read-only in the client

Whoever administers a node (SSH access to it, or physical access if it's local) edits a config file next to mcp-servers.json; the client only lists and selects what that node already declared. The client can never introduce a binary the node operator didn't already choose — a compromised browser tab can pick among entries, not invent one. Costs a hop: adding an agent means touching the node, not the session you're in, and two nodes with different registries now show different pickers with no shared source of truth.

D1-2Custom agents defined client-side per project, pushed over the wire, node holds an allowlist

Matches Zed's ergonomics — define it once in the project, use it everywhere the project opens — but the node still has the last word: it only launches a command/args/env tuple that matches an entry an operator put on its own allowlist first. A compromised client can still only pick from what the node already agreed to run, same guarantee as D1-1, but the definition itself now lives with the project instead of the machine, so it follows the project across nodes. The allowlist has to be edited node-side regardless, so this doesn't remove the operator step, it just moves what travels over the wire.

D1-3D1-2 plus a curated agent registry we maintain

On top of D1-2's client-defined-plus-node-allowlist shape, loombox ships and updates a catalogue of known-good agents (the way the six MCP quick-add presets already work, mcp-presets.ts:56-119) so picking "Gemini CLI" is one click instead of typing a command line. Convenience only — trust still rests entirely on the node's allowlist from D1-2, this option changes nothing about who can execute what. The cost is upkeep: a curated list needs someone to keep it accurate as vendor CLIs change their own invocation.

D2

Where an MCP server actually runs

MCP server config is stored in two places today that never talk to each other. The client keeps a per-project list in localStorage (mcp-server-store.ts:44, key loombox:mcp-servers:${projectPath}), editable from the Config tab's quick-add/custom-server form (+page.svelte:842-845, McpServerConfigPanel.svelte). The node keeps its own project/global record in mcp-servers.json (mcp-config-store.ts:130-132, issue #187, closed) plus a per-(server, secret) grant ACL that never auto-grants (mcp-secret-grants.ts:6-11, issue #189, closed). Neither store launches anything: per issue #627 (open), NodeDaemon.resolveMcpServers only resolves a declared, secret-granted server list into the AcpMcpServerConfig[] that AcpClient.newSession hands to the agent — the agent itself is what speaks MCP to a stdio/http server, loombox never runs one. The one server loombox needs to run itself, the native tracker's tracker_* tools built in issue #211 (closed), has nowhere to run from — that's exactly what #627 is blocked on. Zed's stdio servers carry a remote: bool, and Zed's own SSH remoting is broken for it (their issue #34402) because it assumes the same binary at the same path on both ends. loombox already has the transport a stdio server needs on the far end — the ssh: execution target (target.ts:6-15) — which #627 and any future placement decision can build on directly.

TodayNothing runs — config exists, launch doesn't

A filesystem MCP server pointed at a worktree cannot be added meaningfully yet: the config record can be created and secret-granted, but no process is ever spawned for it and no tool reaches the agent. #627 blocks every option below — it is the first piece of plumbing regardless of which placement wins.

D2-1Node-local only — every server runs beside the node process

Simplest to build: one launch path, one place secrets resolve (resolveMcpServerConfigs already only ever runs node-side, mcp-secret-grants.ts:20-25). A filesystem server pointed at an ssh: target's worktree would be reading a directory that doesn't exist on the node's own disk — it would have to reach the worktree over the same SSH transport a second time, or be pointed at the wrong filesystem entirely. This option is honest that it doesn't solve the SSH case; it just doesn't pretend to.

D2-2On the execution target — an ssh: server runs on that host

A filesystem server pointed at an ssh: worktree runs next to the files it reads, over the deploy-and-detach machinery target.ts:9-11 already documents for the agent binary itself. Solves exactly the case Zed's own SSH story can't — loombox isn't assuming the same binary path on both ends, it's placing the server where the transport already lands things. Secret material still resolves node-side and is injected at launch, never sent to the relay (mcp-secret-grants.ts:20-25), so this changes where the process runs, not where the secret sits. Costs a second thing that can be absent on a remote host: the MCP server binary itself, on top of the agent CLI.

D2-3Both, chosen per server, default follows the target

A filesystem server defaults to D2-2's placement automatically because it needs the worktree; an API-key-only server (Context7, say — already in the preset catalogue, mcp-presets.ts:26-28) has no reason to run anywhere but the node and can stay at D2-1's default. Gets the common case right without a decision the user has to make, but it's the most code: two launch paths, plus the logic that infers which one a given server needs.

D2-4http/sse servers first, stdio later

Sidesteps placement for the first release: an http/sse server has no process for loombox to run anywhere, it's just a URL AcpClient.newSession hands the agent, so there's nothing to place. Ships fastest, but a filesystem-pointed server is exactly the stdio case this defers — the one MCP server type most obviously useful against a worktree is the one this option doesn't touch.

D3

Tool policy

Today there is exactly one policy surface, and it lives at request time. Every tool call an agent wants to make arrives as an ACP session/request_permission, queued FIFO per session (permission-queue-state.ts:3-19), only the head is actionable (isPermissionRequestActionable, permission-queue-state.ts:96-109). Each is answered with one of four option kinds ACP itself defines — allow_once, allow_always, reject_once, reject_always (types.ts:120-121), rendered as flat buttons in PermissionCard.svelte:193-218. Separately, node-side only, a per-project PermissionPolicy of command and network globs exists — deny always wins over allow, empty policy means allow-all (permission-policy.ts:27-53) — enforced at the point a command actually spawns or a terminal line is submitted, not at ACP's own permission request. It has no user interface anywhere: nothing under apps/web/src references PermissionPolicy at all, so today it can only be hand-edited as JSON on the node. Zed keeps two separate concepts: profiles (agent.profiles) decide which tools exist for a thread at all — Write / Ask / Minimal, a bool per tool, plus per-MCP-server tool toggles — and tool permissions (agent.tool_permissions) decide the approval mode per tool, confirm/allow/deny, with always_allow/always_deny regex lists addressing MCP tools as mcp:<server>:<tool>. Whatever ships here has to answer to the fact that the agent, not loombox, owns its own tool list — loombox can gate or auto-answer a request, it cannot add a tool the agent didn't declare.

TodayRequest-time only, plus an invisible glob policy

allow_always already exists and already works — the agent stops asking for that exact tool/target combination for the rest of the session, entirely inside ACP's own protocol, no loombox state involved. The glob policy sits underneath it, unrelated and unreachable: a deny there blocks the process before ACP even gets a chance to ask, so an operator who wants "never run rm -rf, ever" today has to write JSON by hand.

D3-1Keep request-time only

No new UI, no new state to reconcile with allow_always. Leaves the glob policy exactly as invisible as it is today — an operator who wants a standing rule still edits JSON on the node, and there is still no way to say "this session may never touch the network at all" without hoping every permission prompt gets answered correctly.

D3-2Surface the existing glob policy in the UI, no profiles

Cheapest real improvement: a settings surface for the command/network allow/deny lists that already exist and already enforce (permission-policy.ts:27-53) — no new backend concept, just a form over data that's been sitting unreachable since #256. Doesn't touch allow_always at all — it stays exactly as it works today, a separate, faster-acting layer underneath. The two can conflict silently: a session-level allow_always means nothing if the node-level policy denies the command first, and this option ships no UI that explains why an "always allowed" tool still gets blocked.

D3-3Profiles that gate which tools a session may use, on top of request-time approval

Adds Zed's other half without touching the one that already works: a profile trims the tool list a session is even allowed to invoke — Write/Ask/Minimal or loombox's own equivalent — and every tool that survives the trim still goes through the existing FIFO queue with its existing allow_always. A profile can only narrow, never substitute for, the glob policy — a profile that permits Bash says nothing about which commands that Bash may run, so this still leaves the glob policy invisible unless D3-2's surface ships alongside it. Needs a place to declare per-MCP-server tool toggles once D2 lands and there's an actual list of tools to toggle.

D3-4Both — profiles plus rules, matching Zed exactly

Profiles gate existence, the glob policy (surfaced, per D3-2) gates approval mode, request-time allow_always stays the fast path for a one-off "stop asking me this." Closest to Zed's own mental model, which means the most surface to design and explain: three systems (profile, policy, per-request always) that all shape the same "can this tool run" question, and a user has to understand which one answered no before they can fix it.

D4

Remembering the model, the effort and the mode

ConfigOptionStore keeps exactly one option list per live session, keyed by session id, and drops it the moment the session closes (config-options.ts:26-59, clear()) — there is no persistence layer anywhere between sessions. The catalogue itself now round-trips end to end (issues #705, #718, PR #724, all closed/merged 2026-08-05): session/new's options are read instead of discarded, a pick is sent through config_option to a real AgentSession.setConfigOption, and the agent's own config_options push — not an optimistic local guess — is the only thing that updates ConfigBar now. But that fix is scoped to one session's live round trip; it changes nothing about what the next session starts with. ConfigBar.svelte:15-20 says it plainly: "there is no internal 'currently selected' state duplicated here" — it renders whatever the agent just sent, every time, from zero. Zed stores default_config_options per agent in settings, so a fresh thread with the same agent starts where the last one left off.

TodayEvery session starts at the agent's own defaults

Zero state to get stale or leak between projects. Picking Opus and high effort five times in a row for five different sessions means five re-picks — the entire cost this decision exists to remove.

D4-1Keep — no persistence

Ships nothing, changes nothing. Only defensible if the answer to this whole decision is "not yet" — worth saying plainly rather than defaulting into it by not deciding.

D4-2Remember the last used values, per agent, per account

Matches Zed's own shape most directly — one stored triple (model, effort, mode) per provider id, read back the next time that agent starts a session, written the way accent.ts already writes a single account-scoped preference (the same pattern v8's B2-1 picked for the thought-collapse toggle). Wrong the moment two projects genuinely want different defaults for the same agent — a docs-only repo and a production service both get whatever effort was last picked in either one.

D4-3Per project as well, project wins over account

Fixes D4-2's cross-project bleed: a project-scoped override (paired with the project's own MCP config already stored this way, mcp-server-store.ts:44) beats the account-wide last-used value when both exist. Two places to look when a default seems wrong — "why is this session on low effort" now has two possible answers instead of one, and whichever surface ships this has to show which one is currently winning.

D4-4Session templates — target, agent, model, effort, mode, starting prompt

This is issue #259 (open, "Session templates/presets"), not a smaller version of it — #259 already specifies target, provider, MCP set and starting prompt as one saved, nameable unit, created/edited/deleted from the UI, project-scoped or global by choice. Model/effort/mode are two fields short of what #259 already asks for. Picking this option is really picking to build #259 and let config-option memory be one more field on the template rather than its own feature — the cost is that a template is a deliberate save action, not an automatic "remember what I did last."

D5

How much of MCP we consume

loombox's own MCP participation stops at declaration. A client-added server (or, once #627 ships, a node-hosted one) becomes an AcpMcpServerConfig entry (resolveMcpServerConfigs, mcp-secret-grants.ts:134-152) handed to AcpClient.newSession — from there it's the agent binary itself (Claude Code, Codex) that speaks the MCP protocol, lists that server's tools, and decides what to do with its prompts or resources. loombox never lists a server's tools itself, never turns a prompt into a slash command, never shows a resource as attachable context — there is no code path where loombox is the MCP client, only the thing that tells the agent where to connect. Zed's own client does all three: tools ✅, prompts ✅ as slash commands, resources ⚠ listed but not attachable, sampling/elicitation/roots ❌/❌/⚠. Building any of this in loombox means loombox itself becoming an MCP client for the first time, not extending something partial.

Whatever tools/prompts/resources a session gets come entirely from what the agent binary itself supports and chooses to surface in its own transcript output. loombox has no visibility into any of it beyond what the agent already reports as a tool call.

D5-1Tools only

loombox lists a server's declared tools (config already carries enough to attempt a connection and call tools/list) purely for visibility — "this server exposes 3 tools" in the MCP settings row — without changing how a tool call reaches the agent. The smallest real step, and the one every other option needs as a foundation: you can't surface a prompt as a slash command without already knowing how to talk to the server that offers it.

D5-2Tools plus prompts as slash commands

Matches Zed's own scope exactly, and pairs with a composer slash-command system if one ships (a client-side affordance, independent of any agent's own support for it — an MCP prompt becomes a loombox UI action, not an agent feature). Needs a real composer integration point that doesn't exist yet — this is new client surface, not a settings row.

D5-3Tools, prompts and resources as attachable context

Goes past Zed: a resource becomes something a user can attach to a turn the way a file already can. The least verifiable of the three for a first release — resources are the part of MCP loombox has zero code touching today, in either direction, so "attach a resource" means building fetch, caching and an attachment-pill UI for a data shape nobody in this codebase has parsed yet.

Ranked by what a first release can actually verify end to end: D5-1 is checkable the moment a server connects — a tool count either matches tools/list or it doesn't. D5-2 is checkable once a slash command exists to type — the prompt either fires or it doesn't. D5-3 has no existing loombox surface to verify against at all; it would be the first thing built and the first thing tested, not an increment on something already working.

E2

Paced reveal: protecting against a burst, or against nothing

TextPacer reveals a live turn's text on a 32ms tick, at least 2 characters and up to 35% of the outstanding backlog per tick (text-pacer.ts:37-39, the constants; :112-125, the tick itself). It exists so a burst of chunks doesn't dump straight into the DOM and thrash it, per that file's own doc comment. But by the same formula's own arithmetic, a 2,000-character block that already fully decrypted and arrived in one setTarget call still takes about 16 ticks, roughly 512ms, to finish revealing on screen: derived here from the shipped constants, not measured against a real burst. That is the same shape of lag a slow network would produce, except this one is self-inflicted by the render layer, on an agent that answered instantly. Only a genuinely live turn paces at all; replayed history always renders in full the instant it mounts (MessageItem.svelte:22-31).

E3

Where decryption happens

Every envelope this client decrypts goes through one crypto.subtle.decrypt AES-256-GCM call, on the tab's main thread, one at a time. handleSessionUpdate (relay-client.ts:4137-4138) is one of a dozen handlers shaped exactly the same way, each awaiting its own openJson independently instead of collecting a burst first. The chain is openJson to decryptEnvelope to aesGcmDecrypt to crypto.subtle.decrypt (packages/crypto/src/aead.ts:68-85). The account's raw AMK lives as private readonly amk: Uint8Array on the RelayClient instance for the life of the tab (relay-client.ts:1034); getSessionKey derives each session's AES key from it once and caches the resulting CryptoKey (:4835-4842), imported extractable, not non-extractable (aead.ts:20-36's true argument). So a burst's real cost today is N serial subtle.decrypt calls on already-cached keys, not N key derivations.

Today Serial, main thread, no batching

Simplest code, one call-site shape reused a dozen times. Costs a burst of N envelopes being N sequential awaits on the same thread that is also laying out, painting and running Svelte effects.

E3-1 Keep

No change. Costs exactly what Today names, and it gets worse as the burst gets bigger.

E3-2 Batch a burst into one Promise.all

A small change: collect whatever has arrived on the socket in one microtask turn and decrypt it concurrently with Promise.all instead of one call after another. Buys most of the throughput win, since subtle.decrypt is already async and a browser can run several GCM operations at once, without moving a single byte of key material anywhere new. Costs staying on the main thread: a big enough burst can still visibly compete with a paint frame, and the win only shows up when messages actually arrive clustered, which a WebSocket does not guarantee.

E3-3 Move decryption into a Web Worker

Frees the main thread entirely: decrypt runs on its own thread, UI work never waits behind it. This is a real security question, not a pure performance one, so state it plainly. SPEC §8's whole model is about which network peer holds plaintext, device versus relay; it says nothing about isolation between two same-origin JS contexts inside one tab, and a Worker does not create the kind of boundary that stops an attacker who already runs code in this origin: same-origin script can already spawn its own worker or reach the one loombox creates. What does change: the AMK-derived key material now lives in two live JS heaps instead of one, whether the worker re-derives from a copied AMK or every derived session CryptoKey crosses a postMessage to reach it, a second file joins the small set of AMK-touching call sites an audit has to walk, and none of this even trades on non-extractability, since aead.ts already imports these keys extractable (:20-36). Buys the main thread back in full. Costs a second execution context to carry the account's key material through and review, for a boundary that does not actually stop the attacker SPEC §8 is worried about.

E3-4 Worker plus batching

Both changes stacked: Promise.all inside the worker's own message handler. Buys the full throughput win with the main thread fully clear. Costs both of the above at once, the worker's audit surface from E3-3 and the burst-timing dependency from E3-2, for the one option that actually earns "fastest" of the four.
