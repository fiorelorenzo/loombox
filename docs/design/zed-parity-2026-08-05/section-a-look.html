The ground and the direction of layering

Today the dark theme runs rail #08090b, bg #0a0c0f, surface #0e1114, surface-raised #101418 (deck.css:30-33), all within 6 hex points of each other and at essentially zero chroma. The chrome (the rail) is the single darkest value in the set: chrome sits below the canvas, which sits below the cards. Zed's One Dark ground inverts that and adds real color: window #3b414d, panels #2f343e, editor #282c33, a blue-grey around hue 220° with roughly 10% saturation. The editor, the content well, is the deepest point; the chrome floats above it. That inversion plus the chroma is a large share of why Zed reads as a dedicated tool and loombox reads as a dark website. Borders and shadows are a separate question (A3); this is only about which surface is darkest and whether the palette has any hue in it.

Density

--nav-row-height: 2.5rem, 40px, sizes the sidebar's primary destination rows (Inbox, Nodes and targets, Tracker) via .destination-row (tokens.css:71, +page.svelte:4194-4199); a per-session row in a project group has no such fixed height, it is padding-driven. --topbar-height: 3rem, 48px (tokens.css:92). Body text is 0.95rem, 15.2px, and this is not just a chrome number: html sets its font-size to it directly (typography.css:39,89) and a transcript paragraph inherits it with no override of its own, only headings and code get their own scale step (typography.css:62,521). Code/mono text is 0.85rem, 13.6px (typography.css:62). A default `Button` computes to roughly 39px tall (md) or 26px (sm) from its padding and line-height (Button.svelte:240-246), and a whole set of controls (Button, IconButton, Input, Select, Checkbox, the ConfigBar trigger, PermissionCard's answer buttons, PlanCard's header, the theme swatches) already jump to a 44px floor under @media (pointer: coarse), an explicit touch-target contract (Button.svelte:328-337, SPEC.md §7.3, issue #133). Zed's chrome runs ∼13.2px text, 22px default buttons, and a 4px spacing grid with a Compact/Default/ Comfortable multiplier. Any tightening here has to say what happens to the one nav surface with no coarse-pointer floor today, and to the one token that both chrome and prose currently share.

A3

Borders, fills and elevation

Two different mechanisms are already in play today, and they don't have the same gap to Zed. Interactive state (hover/selected on a session row) is already a fill step, not a border change: hover is --color-fill-subtle (6% white), selected is --color-fill (12% white) (+page.svelte:4523-4529), and that part already matches Zed's own idiom. The real gap is the elevation ladder: Card.svelte maps flat to surface + a 9% white border and no shadow, raised to surface-raised + a 16% border and --shadow-sm, floating to surface-raised + a 28% border and --shadow-lg (Card.svelte:60-75). Borders are translucent everywhere, and there's a three-tier shadow scale used well beyond overlays: the composer carries --shadow-md (+page.svelte:5360-5362, settled by v7's A1-3, "the field sits on --color-surface-raised with a soft shadow... do not spread the shadow to other surfaces"), and PermissionCard carries --shadow-lg (PermissionCard.svelte:251-252). Zed uses opaque border colors, a fill step for hover/selected, and essentially no shadow outside a popover or a modal. Any option here that touches shadows has to reckon with the composer's shadow being an already-settled pick, not an open question.

A3-1Keep the hairlines and the shadow ladder

Zero migration risk, and it doesn't reopen v7's A1-3: the composer and PermissionCard keep exactly the lift they were given on purpose. Cost: this is precisely the softness Lorenzo pointed at when he said Zed reads more dev-oriented. Translucent borders and drop shadows read as a web app being careful about elevation; opaque borders read as a tool being precise about layout.

A4

Where monospace is allowed

The base rule is code, kbd, pre, samp, .font-mono go monospace, described in typography.css:101-112 as covering "agent output, code, and diffs." In practice it already reaches further than that phrase suggests: project paths (ArchiveSessionDialog.svelte:108, NewSessionDialog.svelte:238), connected-account hostnames (ConnectedAccountsList.svelte:144), the terminal's cwd/shell/status (InteractiveTerminal.svelte:434-448), diff paths (DiffViewer.svelte:111,114), the file tree (FileTreePanel.svelte:249), the context-usage meter's numbers (ConfigBar.svelte:739, tabular figures per the doc comment at typography.css:22-26), and, already, the topbar's own project/target breadcrumb (+page.svelte:5031). What's still sans: a tool call's own title, e.g. "Read package.json", is a plain <span> (GenericToolRow.svelte:169,308); only its key/value payload fallback goes mono (GenericToolRow.svelte:181,342). A session row's target label and relative timestamp are plain text too (+page.svelte:4582-4588, no font-family rule). Zed is sans-in-chrome, mono-in-buffer by default, but a dev tool reads as a dev tool partly because identifiers are set apart from prose everywhere, not just in the editor.

TodayMono for code, diffs, terminal, paths and one meter, sans for the rest

Inconsistent in a specific way: the topbar breadcrumb is already mono, but a tool call's own title and a session row's target/timestamp are not, so "is this an identifier" gets a different answer depending which row you're looking at.
