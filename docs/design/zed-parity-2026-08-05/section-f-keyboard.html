F1

An action registry

Today the palette opens on Mod+K (keyboard.ts:23-25, wired in +page.svelte:2247-2251), searching sessions plus a hand-built actions array (+page.svelte:1742-1763) merged into one fuzzy list (CommandPalette.svelte:74-89, matched by fuzzy.ts:11-45). Measured live: two actions at rest, "Open attention inbox" and "Open nodes and targets" (+page.svelte:1752-1761). That count is correct for a session with no turn running. A third action, "Stop current turn", is pushed only while the selected session's turn is active (+page.svelte:1744-1751), and it is the only one of the three that carries a shortcut, Mod+.. So the live measurement is right at rest and one action short mid-turn. A row shows its shortcut, right-aligned, only when the action object sets one (CommandPalette.svelte:179-182), and the same string repeats in the footer hint bar (:195-197). Nothing else in the app reads this array: no menu item, no settings row, no other keyboard entry point. Two more real bindings sit outside the palette entirely and are invisible to it: Mod+B toggles the sessions column (+page.svelte:2257-2260), and the three dock resize handles read arrow keys directly while focused (dock-panel.svelte.ts:209-217). Zed's discovery model runs the other way: a fuzzy-matched registry of every capability, the binding shown inline next to it (research digest §6).

Costs nothing to ship today; every new capability is one more object literal in the same function. F1-2 A real action registry

One declaration per capability, an id, a label, a handler, an optional binding, that the palette and every future command surface read from instead of owning its own list. Buys one source of truth and a binding that is finally visible next to the action that owns it. Costs a real refactor: today's topbar buttons and dock toggles each call their own handler directly and would need to become thin callers into the registry instead of the registry mirroring them.

F1-3 Registry plus context

Same registry, and each entry also declares when it can run, so the palette hides or dims whatever would no-op if picked right now: "Stop current turn" only while a turn is active, "Next session" / "Previous session" only with more than one session open. Closest to Zed's own model, and the more honest surface, since a row that does nothing when picked is worse than a row that isn't there. Costs the most: every action needs its availability expressed as a predicate, not just its effect, and that predicate has to keep tracking whatever state it reads as that state's own shape changes.

F2

Which bindings we adopt

Zed's own muscle-memory anchors, from the research digest: Mod+P file finder, Mod+Shift+P palette, Mod+B / Mod+J / Mod+Alt+B for its three docks, Mod+, settings, and, confirmed separately, Mod+Shift+] / Mod+Shift+[ for next and previous tab. VS Code on macOS agrees with almost all of that: same palette key, same quick-open key, same settings key, and the same Mod+J for its own terminal panel, not Ctrl+`, that is the Windows and Linux default. The one place the two genuinely diverge in this list is next and previous tab: VS Code's Mac default is Mod+Alt+Right / Mod+Alt+Left, not the bracket chord, because Mod+Shift+[ hits a documented macOS key-dispatch bug in VS Code's own issue tracker. Three loombox bindings are already spoken for and every option below keeps them: Mod+K opens the palette (+page.svelte:2247-2251), Mod+. stops the turn (:2252-2256), Mod+B toggles the sessions column (:2257-2260). The inbox's j / k and its digit answer are E3-1, settled in the v7 decisions and not reopened here (AttentionInbox.svelte:334-361): unmodified keys, no chord, nothing below touches them. "Cycle model / effort" below reaches the one consolidated control E1-2 already settled in v8, it does not propose a new one. A browser tab, not just the OS, owns a real slice of the keyboard: Mod+N, Mod+T, Mod+W and Ctrl+Tab cannot be stopped with preventDefault() in a normal tab, only inside the Electron shell; DevTools chords (Mod+Shift+I/J/C, F12) are reserved on most browsers too. Rows below are marked where a key is confirmed reserved or genuinely needs a per-browser check; an unmarked row is not a guarantee, it is the set of keys with no known conflict.

F2-1 Keep today's handful

The nine bindings above, unchanged. Zero collision risk, because nothing new is claimed, and zero discoverability gained. This is F1's "add by hand" problem again from the keyboard side: a hand-grown registry and a hand-grown keymap drift the same way, toward whatever the last person remembered to bind.

F3

Customisable keymap

No user-facing remap surface exists anywhere in loombox today. Every binding cited in F1 and F2 is compiled into keyboard.ts, +page.svelte, AttentionInbox.svelte, PermissionCard.svelte and dock-panel.svelte.ts; nothing in apps/web/src/lib/components so much as mentions a keymap or a remap outside comments describing this same fixed set. Zed's own keymap is user-editable JSON matched by context predicates (research digest §6, e.g. Editor && vim_mode == normal) and reachable from its own palette. Changing any loombox binding today means editing source and shipping a release.

Today No remap surface at all

Whatever F2 picks is what everyone gets, forever, until the next release. No escape hatch for the one person whose window manager already owns a chord F2 wants.

F3-1 Fixed bindings, on purpose

Identical to today. Costs nothing to maintain, literally nothing changes. The price is paid by whoever has a real collision: a screen reader chord, an OS shortcut, a browser extension already sitting on the same key, with no way to move off it short of asking for a code change.

F3-2 A small remap surface, loombox actions only

A short list in Settings, one row per loombox-specific action from F1's registry (new session, next/previous session, cycle model, open inbox, and the like), not the browser-standard ones a user is unlikely to want to move. Costs a capture-and-validate control: read the pressed chord, check it against the rest of the live registry for a collision, reject or confirm, store the result per account the same shape accent.ts already uses for a boolean preference. Bounded scope keeps the collision check small, since it only ever checks loombox's own set, never the browser's.

F3-3 A full user keymap, synced

Matches Zed: every action remappable, context predicates possible, stored per account like the rest of loombox's synced state. Two real questions this option has to answer, not gloss over: what happens on a phone, where there is no physical keyboard to record a chord against, so the whole feature has nothing to attach to on the mobile web client; and what happens when a synced binding is free on one device and reserved on another, a chord open on desktop Chrome and taken on mobile Safari, which the JSON format has no field for today. Cost: parsing and validating arbitrary user JSON against a live registry, a hard rule that action ids never get renamed once this ships (F1's registry would have to promise that), and a merge story for the same account editing its keymap from two open tabs at once. 

// keymap.json, per account, synced
