A Space & measure

A1

The measure: readable prose vs. wasted canvas

mi sembra che ci sia un sacco di spazio orizzontale inutilizzato nel body principale

Real, and not an accident. --measure: 90ch (tokens.css:54) drives .items { max-width: var(--measure); margin-inline: auto } (+page.svelte:4930), and .canvas-footer mirrors it (:4994) — the code's own comment says transcript prose used to run the full 1440–1920px canvas at ~150 characters a line (:4924-4926), and 90ch was the fix. At his measured 1182px canvas that comes out to an 863px column, so roughly 320px sits empty on the two sides combined. A wider --measure-wide: 120ch token already exists for code, diffs and terminal output — DiffViewer and PageLayout both use it (DiffViewer.svelte:100, PageLayout.svelte:54) — but inside the transcript itself .items caps the whole <ol> at 90ch, narrower than 120ch, so a diff nested in a tool-call row can never actually reach its own wider cap. The wide measure is already written; it just can't fire where he's looking. In the mocks below the accent block is the content column and the amber dashed patch is where it collides with something else.

TodayOne fixed measure — 90ch, everywhere

Correct today, but only in isolation: a single 90ch cap has no way to know a code block or a whole canvas isn't prose, so everything pays the readability tax whether it needs it or not.

Not a missing feature — a broken wire. ConfigBar already exists as SPEC.md §7.24 “Model, mode & reasoning effort”'s specified home for exactly these two controls, mounted in the one row under the composer since Lorenzo's own July 30 request put it there. It renders only the agent name and the cost meter today — I read the live DOM and it is literally Oh My Pi + $0.00 — because options is always empty. client.ts:432 seeds every new session from this.lastConfigCatalog, and that field is populated only by initialize (:408); session/new's own response is typed as a bare { sessionId: string } (:427), so whatever catalogue it carries is never even parsed. Probed against the real omp acp binary directly: initialize returns no configOptions at all — session/new is where the real catalogue lives, 26 models, thinking (off/auto/low/medium/high/xhigh/max), mode (default/plan). There's a shape to bridge too: the wire sends {id,name,category,type,currentValue,options:[{value,name,description}]}, the internal AcpConfigOption (types.ts:158) is {category,current,choices:[{id,name}]}. Read session/new's response and map that shape, and “le opzioni giuste per ogni provider” comes for free — the agent declares its own catalogue per provider; loombox's only job is to stop discarding it and render whatever arrives. What's left to decide is presentation: 26 models and 7 thinking levels is a lot to fit under one composer row. Every option below also carries a second, orthogonal fork: session/set_config_option changes the running session only — nothing in the client persists a choice past it, so a “remember for new sessions” checkbox is new plumbing, not a flip of a switch that already exists. Both, same cause, and it is the bug I already fixed once. A node keeps a SessionBridge per live session, created in exactly one place (node-daemon.ts:1905, inside session creation) and never rebuilt for a session that was already on disk. Eleven handlers open with if (!bridge) return; — fs_list_request (:2836), terminal_open (:3947), terminal input/resize/close, the three test-runner handlers, run_start, run_cancel and prompt_inject. So the moment the node restarts — a deploy, a crash, a reboot — every pre-existing session keeps rendering its transcript from the client's own cache while every one of those requests is dropped without a reply. The client waits out its own 10s deadline (FileTreePanel.svelte:82, InteractiveTerminal.svelte:293) and then blames the node for being asleep or offline, which is exactly the wrong thing to tell you: the node is awake, connected, and ignoring you.

This is the same defect class as #697, the tracker bug you found last round. That fix removed the guard on one handler and left the other eleven. The comment it left behind at :2922-2925 even says so out loud. Better yet, the terminal handler's own doc comment promises the opposite of what the code does: “so the client never hangs waiting for a reply that never comes”, three lines above the return that hangs it.

And the node already knows. A session reloaded from disk after a restart comes back marked 'disconnected' on purpose, with the reasoning written out at session-manager.ts:49-53: “a node restart means the agent process that made a saved 'running' or 'paused' record true is simply gone, and pretending otherwise would let a client believe it can resume into a live agent that no longer exists”. That is exactly right, and then nobody tells you. The client draws the session like any other, offers Files and Terminal, and the handlers meet both with silence — so the one honest piece of state in the system never reaches the screen.

The tool-call glyph sits below the line it belongs to

le icone dei comandi eseguiti di quando esegue un tool non sono allineate con il testo del comando

Real, and it is one declaration. .tool-gutter carries padding-top: var(--space-2xs) (ToolCallGutter.svelte:27) inside a row that is already align-items: flex-start. The row aligns the gutter's top edge to the command's top edge correctly, and then that padding pushes the glyph 4px down from it, so it lands between the first and second line instead of on the first. The padding is decorative; the gutter's real job, keeping the glyph flush to the column's right edge, is done by align-items: flex-end and is unaffected by removing it.

The terminal prints its own plumbing before your prompt

quando funziona ci sono delle righe in alto di testo prima della riga per i comandi che non c'entrano niente

Found it, with one honest caveat. On an SSH target the node writes cd <worktree> && clear into the shell channel and only then wires the output listeners (node-daemon.ts:4049, listeners at :4053), so that command and whatever the login shell printed before it are already in the buffer when the client attaches. The code comment calls this “an accepted, documented tradeoff”; you are the evidence that it is not accepted. It exists because ssh2's shell channel has no cwd option, unlike a local node-pty spawn.

The caveat: your session is a local target, and the local branch has no such write — I opened a terminal on it and got a single clean prompt row and nothing else. So either you saw this on an SSH target, or there is a second source I have not reproduced. Worth one sentence from you before I fix the wrong thing.
