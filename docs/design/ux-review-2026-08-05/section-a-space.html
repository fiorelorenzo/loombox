The measure: readable prose vs. wasted canvas

mi sembra che ci sia un sacco di spazio orizzontale inutilizzato nel body principale

Real, and not an accident. --measure: 90ch (tokens.css:54) drives .items { max-width: var(--measure); margin-inline: auto } (+page.svelte:4930), and .canvas-footer mirrors it (:4994) — the code's own comment says transcript prose used to run the full 1440–1920px canvas at ~150 characters a line (:4924-4926), and 90ch was the fix. At his measured 1182px canvas that comes out to an 863px column, so roughly 320px sits empty on the two sides combined. A wider --measure-wide: 120ch token already exists for code, diffs and terminal output — DiffViewer and PageLayout both use it (DiffViewer.svelte:100, PageLayout.svelte:54) — but inside the transcript itself .items caps the whole <ol> at 90ch, narrower than 120ch, so a diff nested in a tool-call row can never actually reach its own wider cap. The wide measure is already written; it just can't fire where he's looking. In the mocks below the accent block is the content column and the amber dashed patch is where it collides with something else.

TodayOne fixed measure — 90ch, everywhere

Correct today, but only in isolation: a single 90ch cap has no way to know a code block or a whole canvas isn't prose, so everything pays the readability tax whether it needs it or not.

One universal number stays the simplest rule to reason about, and it still respects the readability ceiling the cap exists for — but it only buys back part of the emptiness at his width and gets relatively worse again on anything wider, and it does nothing for code, diffs or terminal rows, which stay exactly as narrow as prose for no reason.

A1-2Split the measure by content type

Recommended. Prose keeps exactly the measure that's already correct; code, diffs, tool rows and terminal output stop pretending to be prose and take the width they actually need. Trades one uniform rhythm down the transcript for two, in exchange for a --measure-wide token that's already declared in the codebase but currently can't do anything — this is what makes it real.

A1-3Scale the measure with the viewport (clamp)

A2

Column centring when a side panel opens

mi da anche fastidio che quando i due pannelli laterali sono aperti il contenuto e l'input non sono centrati

Measured over CDP at his 1470px window. Panel closed: canvas spans 288→1470 (1182px), column 447→1311 (863px) — centred inside the canvas, and .canvas-footer (input included) shares the identical rule (+page.svelte:4994), so it moves with it. Panel open: canvas shrinks to 288→1087 (799px, the 383px panel takes the rest), column 303→1072 (769px) — still perfectly centred inside the canvas. Nothing here is uncentred by the code's own arithmetic. What he's actually seeing: the canvas is flush against the left rail and only its right edge moves, so opening one 383px panel drags the whole canvas — and everything centred in it — 144px left, while shrinking the column by 94px, in the same frame. A shift and a resize at once is what reads as "not centred," more than either alone would. In every mock below the accent block is the content column and the amber dashed patch is where it collides with the rail or the panel.

TodayCentred in the canvas, wherever the canvas is

Mathematically fair — always dead centre inside whatever the canvas currently is — but the canvas itself isn't centred in the window, and it moves and narrows the instant a panel opens, so "centred" stops feeling true exactly when it matters most.

A2-1Centre on the window, not the canvas

Locks the column to the window's real midpoint, so it finally reads as centred to the eye that's judging it against the whole screen. It no longer respects the canvas's own right edge to get there, so with a panel open it can crowd into — and here, slightly under — that panel.

A2-3Anchor to a fixed offset from the left rail

The most literal answer to "never moves": position and width both pinned to the closed-panel geometry, so the panel is the only thing that ever moves. It has no way to yield when a panel actually opens, so the collision is total rather than a few pixels — this only works paired with a hard rule for what happens below the width where it no longer fits at all.
