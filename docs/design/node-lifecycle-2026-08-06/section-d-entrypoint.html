D1

Who performs the install, and from where

The epic's shape is "setup happens from the GUI, as part of connecting". For an ssh target that works, because the acting node drives the remote over ssh. For a local node it needs something already running on that machine, and the only candidate is the desktop app. That is fine on your Mac and impossible on this devbox, which has no GUI at all and is exactly the machine that keeps losing its node. Whatever we build, the mechanism underneath is the same plan/execute pair; this decides which front doors exist.

TodayNeither: a human writes a unit file

Which is what I did tonight, and why we are here.

D1-1Desktop app only, as part of importing a local project

Buys: exactly the epic's ask, nothing typed, one flow. Costs: a headless server can never install a node, so the devbox stays hand-managed forever and every server-side node in the future needs a Mac or a desktop session to exist.

D1-2A CLI as the mechanism, the GUI as the front door that calls it

loombox-node install | status | uninstall, with the desktop app driving the same code in-process during project import. Buys: one implementation, two entry points, and a headless box is a first-class citizen: the devbox, prodbox, any VPS. It also gives us a way to test the whole flow in CI without a GUI. Costs: a CLI surface to design and keep documented, and the packaging question from A1 has to be answered for it to be installable at all.

D1-3CLI first, GUI wiring as a follow-up issue

Buys: the fastest route to a supervised node on the machines that are broken now, and the GUI lands on top of something already proven. Costs: for a while the product story is still "run this command", which is what we are trying to stop saying.
