A What runs

A1

What the service actually runs

This is the decision that blocks all three platforms at once, and the reason "install a supervised node" has never landed. No package in this repo emits JavaScript: every build script is tsc --noEmit, there is no dist/, no bin entry, no publishable CLI. The node runs one way only, as tsx src/main.ts from inside the monorepo. Meanwhile the systemd unit we generate for an ssh target points its ExecStart at $HOME/.loombox/supervisor/supervisor-bin, a signed artifact that nothing in this codebase produces: supervisor-artifact.ts declares the SupervisorArtifactSource interface, no implementation exists, and apps/desktop/.../provision-target-bridge.ts says so in its own doc comment while resolveProvisionTargetDeps returns undefined forever. Two native dependencies decide how hard each option below is: node-pty (terminals) and @napi-rs/keyring (secrets at rest).

TodayNothing to install, so nothing installs

The ssh path can generate a perfect unit and has no bytes to point it at. The devbox node I fixed tonight points at node_modules/tsx/dist/cli.mjs inside my working checkout, which is honest for my machine and shippable to nobody.

A1-1Run the checkout in place, with tsx

Buys: works today, zero new infrastructure, and it is exactly what my devbox unit already proves. Fine for a developer who has the repo anyway. Costs: the service is welded to a working tree. A git pull, a rebase, a half-finished branch: the next restart runs whatever is on disk, which is precisely the drift #653 was opened about. It also cannot be the answer for a user who never clones the repo, so it is not a step towards the product, it is a step beside it.

A1-2A versioned JS bundle in ~/.loombox/versions/<version>/, with a current symlink

One esbuild bundle per release, plus the two native modules as prebuilt binaries beside it; the unit points at ~/.loombox/versions/current/node.mjs through the system Node. Buys: updates become the thing #656 asks for and prod already does for the web bundle: unpack the new version next to the old one, flip a symlink, restart, roll back by flipping it back. Nothing is ever half-updated, and the running node no longer depends on a checkout. Costs: a real build+publish pipeline (bundle, per-platform native modules, signing, a place to download from), and the node needs a Node runtime present. That last one is already true for the ssh path, which has a runtime_bootstrap step that installs Node when missing.

A1-3One signed single-file binary per platform

Node SEA or bun build --compile, shipped as a GitHub release asset, verified against a pinned key exactly like supervisor-artifact.ts already describes. Buys: the best install story by far, no runtime prerequisite, and the artifact story the existing code was written for. Costs: the two native modules are the whole problem, and a 3 platforms x 2 architectures matrix has to be built and signed on every release before anyone can install anything. Slowest to first working install.

A1-4A1-1 now for developers, A1-2 as the product path

Ship the local backend against a checkout first, so Linux and macOS survival land this week and the seam gets designed against two real platforms; keep the artifact shape (A1-2) as the next issue, with the backend already asking "where is the executable" through one function so switching is a one-line change. Costs: two install shapes exist for a while, and the discipline to actually finish the second one.

B Platform order

B1

Which platform gets the local backend first

The epic fixed the order on 4 August: ssh remote and macOS local (#654) first, then Linux local (#658), then Windows (#659), so the shared seam is designed against two real implementations rather than guessed from one. Since then two things changed. The case that actually keeps biting is Linux (my devbox node has died twice), and I can verify a Linux backend end to end from here, while macOS needs the Mac in the loop for every run. Worth knowing before choosing: launchd is already written (launchd/launchd-provisioning.ts, plist generation, plan/execute, 301 lines of tests) and called by nothing, and systemd is already written and called only through an ssh transport, while LocalProcessTransport already implements that same transport interface against the local machine. Neither platform needs its mechanism invented; both need it reached.

TodaymacOS first, per the epic

#658 says in its own body that it is blocked on #654, which introduces the seam. Nothing has started on either.

B1-1Keep the order: macOS local first

Buys: the plan stays the plan, and the seam is designed against the platform whose vocabulary is furthest from systemd's, which is a real argument. Costs: every verification round trips through the Mac, and the machine that is actually broken stays broken longest.

B1-2Invert: Linux local first, macOS immediately after

Buys: the first backend is the one I can prove here, including the parts that only show up on a real machine (linger, PATH under a service manager, reboot). The seam still gets two implementations before it is called done, because launchd follows straight after with its generator already written. Costs: the seam's first draft is shaped by systemd, and launchd has to push back on it a few days later. Mitigated by the fact that the launchd code already exists, so its vocabulary is known now, not discovered later.

B1-3One pass: the seam plus both backends together

Buys: the interface is written against systemd and launchd simultaneously, which is what the epic wanted from the ordering in the first place, and there is no window where one platform is supervised and the other is not. Costs: a bigger change to review, and the macOS half cannot be verified without Mac time in the same sitting.

C Secrets

C1

Where the node's secrets live once it is a service

A resident node needs a relay URL, a node id, something that proves who it is, and a way to get the account master key. Today the ssh path writes all of them as Environment= lines inside the unit file, which means systemctl cat loombox-node prints the recovery code, and so does any backup of ~/.config. My devbox unit already deviates: it uses EnvironmentFile= pointing at a 0600 file. The zero-touch ssh flow has a third shape it already uses for the AMK: a one-shot wrapped handoff file the node consumes and deletes on first boot. Note this interacts with #815: the device identity itself is currently kept in a kernel keyring that a reboot wipes.

TodaySecrets inline in the unit file

Readable with one command, copied by every config backup, and shown in full whenever anyone pastes a unit into a chat to debug it.

C1-1A 0600 environment file the unit references

Buys: the unit becomes shareable and diffable, the secret sits behind file permissions, and it works identically for systemd and launchd. Same discipline as identity.json. Costs: a long-lived recovery code still sits on disk in plaintext, which is exactly what the recovery code is not supposed to be.

C1-2One-shot handoff: a device token plus a wrapped AMK, consumed and deleted

What zero-touch ssh provisioning already does (LOOMBOX_WRAPPED_AMK_FILE, deleted after the node unwraps it with its own device key). Buys: no durable secret at rest: after first boot the machine holds a device token and a keypair, not the recovery code, and the token can be revoked from the account without touching the machine. Costs: it only works if the device identity is genuinely durable, so #815 has to be fixed first or this silently degrades into "re-pair on every reboot".

C1-3Everything in the OS keyring, nothing in the unit

Buys: one storage story for every secret the node holds. Costs: on a headless Linux box the "OS keyring" is a kernel keyring that does not survive a reboot (#815), so this is the option that looks strongest and is currently the weakest here. Viable only after the keyring backend is made to prove it is durable.

D Who installs

D1

Who performs the install, and from where

The epic's shape is "setup happens from the GUI, as part of connecting". For an ssh target that works, because the acting node drives the remote over ssh. For a local node it needs something already running on that machine, and the only candidate is the desktop app. That is fine on your Mac and impossible on this devbox, which has no GUI at all and is exactly the machine that keeps losing its node. Whatever we build, the mechanism underneath is the same plan/execute pair; this decides which front doors exist.

TodayNeither: a human writes a unit file

Which is what I did tonight, and why we are here.

D1-1Desktop app only, as part of importing a local project

Buys: exactly the epic's ask, nothing typed, one flow. Costs: a headless server can never install a node, so the devbox stays hand-managed forever and every server-side node in the future needs a Mac or a desktop session to exist.

D1-2A CLI as the mechanism, the GUI as the front door that calls it

loombox-node install | status | uninstall, with the desktop app driving the same code in-process during project import. Buys: one implementation, two entry points, and a headless box is a first-class citizen: the devbox, prodbox, any VPS. It also gives us a way to test the whole flow in CI without a GUI. Costs: a CLI surface to design and keep documented, and the packaging question from A1 has to be answered for it to be installable at all.

D1-3CLI first, GUI wiring as a follow-up issue

Buys: the fastest route to a supervised node on the machines that are broken now, and the GUI lands on top of something already proven. Costs: for a while the product story is still "run this command", which is what we are trying to stop saying.

E Uninstall

E1

What uninstall removes by default (#814)

You asked for this tonight and it is now filed as #814. The decision worth taking up front is what the default does, because it is the one people click without reading. The footprint on Linux is: the unit and its wants symlink, linger, ~/.loombox/node/ (identity, device token, sessions, mcp secrets, permission policies, agent profiles, spend caps, connected accounts), the keyring entry, ~/.loombox/supervisor/, and ~/.loombox/remote-sessions/ on every ssh target this node ever drove, plus the device registration on the relay, which no local rm -rf can reach.

TodayNo uninstall exists locally; the ssh one keeps files by default

decommission.ts stops and disables the unit and revokes the target, and only deletes files when the caller opts in. Nothing equivalent exists for a local node.

E1-1Default removes the service, keeps the data, always revokes the device

Buys: the safe default. Reinstalling later adopts the existing identity and session history instead of starting a new device. Costs: a machine you meant to wipe still holds session transcripts and secrets until you run the second, explicit step.

E1-2No default: the flow always asks, service or everything

Buys: nobody deletes transcripts by accident and nobody leaves secrets behind by accident. Costs: a question every time, including in the scripted and CI paths, which then need a flag anyway.

E1-3Default removes everything, with a keep-data flag

Buys: "uninstall" means the machine is clean, which is what the word implies and what you asked for tonight. Costs: irreversible by definition; a mis-click destroys local session history that exists nowhere else, since the relay only holds ciphertext it cannot read.

DoneYour devbox node is a supervised service again

A hand-written systemd --user unit: EnvironmentFile at 0600 for relay/node-id/recovery code, mise shims on PATH (without them the node cannot find the agent binaries it spawns), Restart=always, KillMode=process so stopping the node does not kill the agents it started, and linger enabled so it comes up at boot without a login. Proven, not assumed: kill -9 on the main pid, back up and reconnected to prod five seconds later. This is a patch on one machine, and it is the thing the decisions above replace.

#815The node's identity does not actually survive a reboot

It lives in a kernel keyring (/proc/keys shows it, 354 bytes, and the persistent keyring expires after three days), while identity.json from 25 July sits on disk being ignored, because load() never reads the file once an OS backend answers. So the node comes back as a different device. I restored the old identity by hand tonight. Filed P1.
