Every visual decision from your feedback on v0.2.0, each with what the app does today and two to four ways it could work instead. Nothing here is built yet. Pick one per decision and I will put them on the board as specified issues.

The red dashed card is always what ships today, rebuilt faithfully from the current code so the comparison is real. Every option says what it trades, not only what it looks like.

How to answer

  1. Go through the decisions in order. Each has an id like B1.
  2. Pick one option per decision, by id: B1-2.
  3. If nothing fits, say so on that decision and what is missing. That is a useful answer, not a failure.
  4. Reply with just the list, for example A1-1, A2-3, A3-1, B1-2, B2-1, ...

How a turn is delimited

non mi piacciono le card dei messaggi dell'utente e dell'agente. Per niente.

Both roles get a filled, rounded box. .message-item.user sets background: var(--color-surface-raised), border-radius: var(--radius-md) and padding-inline (MessageItem.svelte:402-406), and its gutter also draws box-shadow: inset 2px 0 0 0 var(--color-accent) (:409-411). .message-item.agent/.thought get the same radius and padding on --color-surface instead (:421-427). C Tool calls

C1

The resting state of a completed tool call

non mi piace neanche tantissimo la card del tool use, anche se ho visto solo bash. Al momento mi sembra che sprechi troppo spazio.

BashWidget defaults its body open for every call, regardless of outcome (let expanded = $state(true), BashWidget.svelte:47), and TerminalOutput prints the whole string with no cap ({#if output}<pre class="body">{output}</pre>{/if}, TerminalOutput.svelte:62-64; its own style block at :104-111 sets no max-height and no overflow-y anywhere). #576 already removed the double box (ToolCard.svelte:47-64: a bash call renders with surface={false}, so TerminalOutput's own dark screen is the one surface it gets, not a second card around it), which is a real fix: it closed 2026-08-03, one day before this review. What's left is that a completed call costs exactly what its output costs, whether or not that output is worth reading. Measured against the app's own real tokens (typography.css:39,89: html sets font-size: var(--text-body-size) on itself, so the app's actual root is 15.2px, not the 16px browser default): a pwd with a one-line answer costs 106px; the identical shape around a passing 13-line vitest tail, output nobody needs to read since it went green, costs 393px. Neither figure includes the 8px gap to the next row (.items' gap: var(--space-sm), +page.svelte:4817-4829).

When the output is the point: failures and long tails

Today doesn't branch on outcome inside the render path: the same unconditional <pre>{output}</pre> (TerminalOutput.svelte:62-64) prints a failure exactly like it prints a pass, just with the status chip turned bold and red (ToolCallStatus.svelte:66-75, the one state #576 decided should shout, while completed drops its label entirely at :39-49). That part is correct, a failure is exactly when a card should spend its space, but there is still no ceiling on it: neither the header rule (TerminalOutput.svelte:78-84) nor the body rule (:104-111) sets a max-height or overflow-y anywhere. A failing tsc --noEmit with a realistic 15 lines of errors already costs 481px, measured the same way as C1's numbers; a genuine stack trace or a full suite failure would keep growing the transcript by exactly as many lines as the agent printed, with no way to keep reading the turn underneath it while it's still on screen.

C3

A burst of five to fifteen calls in one turn

Nothing groups adjacent tool calls today. F4

The board itself

The board renders its columns as done, in-progress, todo, left to right. That is alphabetical order [...] It is still wrong: a kanban's columns are a workflow, and reading it right to left to follow work is the opposite of what every board a user has ever seen does.

TrackerBoard.svelte:52-56 derives columns as [...groups.keys()].sort(), alphabetical exactly as issue #651 describes, and a status with zero records never appears at all since groups only has the keys groupByWorkflowStatus actually saw (tracker-record.ts:206-219). Desktop columns are fixed flex: 0 0 18rem (TrackerBoard.svelte:195) inside an overflow-x: auto row (:184-189): three columns already fits most laptops without scrolling, but six would not (6 × 18rem plus five 0.75rem gaps is close to 1790px, wider than a 1440px laptop screen). Mobile (≤767px) already has a real answer, one column at a time with Prev/Next (:236-265, exercised by tracker-mobile.spec.ts:95-128); #651 requires that order to follow the workflow sequence rather than the alphabet, so it doesn't need reinventing, only re-feeding.
