Mi immagino che ci debbano essere dei prompt per collegare account jira e github se non già collegati, e di collegare un tracker per il progetto oppure usare quello locale.

A project with no tracker chosen gets no invitation anywhere. TrackerPage.svelte:237-241 renders a bare EmptyState ("This project has no tracker records yet.") with a single "New record" button: no mention of GitHub, Jira, or that a choice even exists. That is also the only thing the destination ever shows, because readTrackerSnapshotForBridge (node-daemon.ts:2876-2887) always reads from the local NativeTrackerStore regardless of what mode a project is set to (issue #631 confirms the live GitHub/Jira backends are still not wired to the account registry at all). The one surface that does ask native-or-live, TrackerConfigPanel, sits inside Config, a sub-tab of the collapsible right sidebar (ProjectConfigPanel.svelte:92-99). Pick Live there with no account connected and the only way out is TrackerConfigPanel.svelte:206-214's "Use native mode instead" button; connecting an account is an unrelated flow, in Settings → Accounts (SettingsPage.svelte:209-211, ConnectedAccountsSection.svelte:123-142).

F3

Managing issues with the local tracker

Quando si usa quello locale la gestione degli issue e dei tipi deve essere più intuitiva.

Creating and editing a record already has a real, generic form: TrackerRecordDialog.svelte picks a Type, then renders one Field per role that type maps (visibleRoles, TrackerRecordDialog.svelte:89-91), reached from the page header's "New record" button (TrackerPage.svelte:219) or a card's own title (TrackerCard.svelte:80-87). Type management has no comparable surface to be faithful to, so the today card below is what exists instead: TrackerDefineTypeDialog.svelte is a one-way form asking for an id, a label, and for each of the four roles a raw text input naming the exact fields key that role maps to (:135-151, e.g. "Status field" expecting you to already know your own record shape well enough to type status). Its own client interface, TrackerTypeClient (TrackerPage.svelte:70-73), exposes only defineTrackerType: no update, no list, no delete. Once a type is saved there is nowhere in the app to see it again, only its label quietly appearing in the Type dropdown next time.

F4

The board itself

The board renders its columns as done, in-progress, todo, left to right. That is alphabetical order [...] It is still wrong: a kanban's columns are a workflow, and reading it right to left to follow work is the opposite of what every board a user has ever seen does.

TrackerBoard.svelte:52-56 derives columns as [...groups.keys()].sort(), alphabetical exactly as issue #651 describes, and a status with zero records never appears at all since groups only has the keys groupByWorkflowStatus actually saw (tracker-record.ts:206-219). Desktop columns are fixed flex: 0 0 18rem (TrackerBoard.svelte:195) inside an overflow-x: auto row (:184-189): three columns already fits most laptops without scrolling, but six would not (6 × 18rem plus five 0.75rem gaps is close to 1790px, wider than a 1440px laptop screen). Mobile (≤767px) already has a real answer, one column at a time with Prev/Next (:236-265, exercised by tracker-mobile.spec.ts:95-128); #651 requires that order to follow the workflow sequence rather than the alphabet, so it doesn't need reinventing, only re-feeding.

TodayAlphabetical, and an empty status can't render at all

"Done" sorts before "In progress" and "Todo", so the board reads the workflow backwards, and a fourth status with no cards yet would simply not show up as a column.
